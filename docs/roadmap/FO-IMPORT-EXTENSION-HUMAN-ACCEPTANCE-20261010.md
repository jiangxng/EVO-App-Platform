### 关键概念，避免验收误判

1. **“未映射列已保留”不等于“正式业务扩展字段已经建立”。**前者保留在导入作业的原始 source；后者需要企业扩展 Definition/Slot、有效 Schema、权限、Import Mapping、extension value sidecar 和后续读取/显示。它们用途、生命周期、权限和检索路径不同。
2. 当前 `DataImportJob.source` 是可查询的企业资源，但**不保证在 Eidos 页面上逐行展示未映射列的原始值**。已有页面主要显示未映射列名/保存状态。历史记录保留 ≠ 不受任何后续归档/保留策略影响的永久业务归档。
3. 正式扩展值没有理由自动进入 EVO Ledger / 成本核算 / Posting Rule；必须通过明确业务语义和批准的映射，才可用于业务效果。
4. 未确认存在完整的「从未映射源列一键生成企业扩展定义、回填历史业务对象」的 Human UI 与安全迁移流程。**这是产品体验补齐候选，不是 CP-03 的现有已验收功能**；做该功能应独立设计：类型推断建议 → 人工确认 Slot/权限/唯一键 → 原数据回填预览 → 批量幂等提交/审计。
5. Counterparty 正式导入流程包含 Human 确认和保存 Recipe；EC 只做 advisory，不得从未经确认的未知列直接创造字段或写业务实体。

## 最小可复现步骤与证据保留

- 在登录状态、合法测试 Enterprise Context 下打开 `/data-import`；选择 Supplier 的导入目标；使用样例 A（3 行），检查两列未识别字段是否没有被误映射。
- Dry-run 记录：测试 Context、Import Job ID、3/0 统计、截图（遮盖个人/企业敏感资料）。确认测试环境隔离后执行 commit。
- 查看 `/data-import/jobs/{id}`（实际页面如改版应以产品导航为准）；确认原始来源标记。查看供应商列表，以唯一测试编码逐一检查 `SUPPLIER` role、主体名称。
- 样例 B（2 行）先**只预检查不提交**，观察 `RECIPE` 来源和正确列映射；需要测试正式保存时再人工确认。

- 新增回归：`tests/protocol/data-import-human-experience.test.mjs` 的 CP-03D 既有 Human-first recipe 测试额外断言「成功提交后的 Job 仍有未映射备注原值，且没有写到 Counterparty.notes 或 Enterprise Extension Value」；[Platform CI #38059144873](https://github.com/jiangxng/EVO-App-Platform/actions/runs/38059144873) 已成功；这仅验证协议断言，不表示 Human 已重新点击生产页面验收。

## 证据与用户只需要确认的判据

只要用户能够从**实际 Eidos 产品**完成「上传 → 看懂/调整映射 → 预检查 → 明确提交 → 找回供应商 → 读到正式扩展字段（在已有定义的情况下）」，基础对象业务体验就具备一个可复现的用户回归验收点。P0-1/2 与 P0-3 应分别签署结论，不能用单个“导入成功”遮盖扩展字段未落地的疑问。
