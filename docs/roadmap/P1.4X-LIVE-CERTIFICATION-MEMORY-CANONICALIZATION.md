## 2. Live findings

The checkpoint exposed three separate implementation gaps.

### 2.1 Repeated READ convergence was too aggressive

The runtime correctly suppressed an identical successful READ, but then passed an empty tool catalog to the model. This prevented the Agent from choosing a different authoritative READ required to continue the same task.

Closed by PR #84.

### 2.2 Proposal WRITE could not be authoritatively read back

A later Agent turn could not verify a known Memory Proposal ID from Host truth and therefore had to treat the prior action as unverified.

Closed by PR #84 with current-Context read-only Memory proposal lookup.

### 2.3 Content supersession was not canonical deduplication

`supersedesMemoryId` is a real content-revision relation. It is not sufficient for converging two already-existing duplicate Memories onto one existing canonical Memory.

PR #85 made content supersession effective in ordinary retrieval while preserving exact-ID historical reads.

PR #86 added a separate append-only duplicate-to-canonical governance relation.

## 3. Canonicalization model

The desired relation is:

```text
A --canonicalized_to--> B
```

Invariants:

- A remains immutable.
- B remains immutable.
- no third Memory C is created;
- the relationship is append-only governance history;
- Personal Agent may only stage a proposal;
- Human acceptance is required before the relation affects retrieval;
- ordinary retrieval hides an accepted duplicate;
- exact-ID audit can still address both A and B;
- one duplicate cannot have multiple active canonical targets;
- cycles are rejected.

Expected behavior:

```text
Before Human accept:
ordinary retrieval = A + B

After Human accept:
ordinary retrieval = B

Historical exact-ID audit:
A + B
```

## 4. Human review boundary

Personal Agent can stage a non-authoritative canonicalization proposal using the formal Host tool.

The proposal appears in:

```text
Personal Agent → Review Memory
```

The review item exposes:

- duplicate Memory ID;
- canonical Memory ID;
- reason;
- before/after retrieval effect;
- explicit notice that no Memory content is created, edited or deleted.

Accept and Reject are Human-confirmed actions.
