# P1.6 Run-backed Personal Agent Experience Integration

**Status:** ACTIVE  
**Date:** 2026-09-28  
**Predecessor:** P1.5 Durable Agent Operations — LIVE PASS

## 1. Goal

P1.5 proved that durable Agent Runs can outlive browser requests, reconnects and Railway process restarts.

P1.6 moves that durable orchestration into the normal Personal Agent experience.

The Human should keep using Personal Agent as a chat-like experience.

The Human should not need to understand or manually operate:

- run.start;
- run.get;
- run.resume;
- bounded slices;
- process-restart recovery.

Those are transport/orchestration details owned by Eidos + Host.

## 2. Core invariant

```text
The interaction feels like chat.
The execution is a durable Agent Run.
```

The UI must not become the source of truth for run progress.

## 3. Current compatibility state

Backend already exposes:

```text
enterprise-agent.run.start
enterprise-agent.run.get
enterprise-agent.run.resume
enterprise-agent.run.list
```

Legacy synchronous path:

```text
enterprise-agent.chat
```

remains available during migration.

Do not remove it until the run-backed interaction path is production certified.

## 4. P1.6A — Eidos run-backed chat orchestration

The first slice migrates the Personal Agent chat send flow.

Expected interaction:

```text
Human sends message
→ Eidos calls run.start
→ receives runId + PAUSED/SUCCEEDED
→ if PAUSED, Eidos automatically calls run.resume
→ renders durable progress
→ repeat bounded resume requests
→ terminal state
→ render final Agent reply
```

The Human does not manually click “resume”.

## 5. Run state in the UI

Eidos may keep ephemeral presentation state, but durable orchestration truth comes from Host run state.

Minimum client state:

- runId;
- source interaction ID;
- current displayed state;
- whether a resume request is currently in flight.

Do not duplicate:

- model decisions;
- tool observations;
- receipt truth;
- authoritative run state.

## 6. Refresh / reconnect

If the page refreshes or transport disconnects while a run is non-terminal:

1. recover the known runId from the interaction/thread state;
2. call run.get;
3. render the durable state;
4. if PAUSED and Human authority permits continuation, resume automatically;
5. never recreate the original run merely because the browser lost its request.

If runId itself cannot be recovered locally, P1.6 may use scoped run.list to locate recent non-terminal runs only under an explicit deterministic matching rule.

Do not guess across unrelated runs.

## 7. Terminal states

### SUCCEEDED

Render the durable final reply.

### BLOCKED

Render the blocker and the exact Human/authority input required.

Do not auto-resume until the boundary is resolved.

### FAILED

Render the durable error state with retry/restart options that preserve existing receipts and domain evidence.

### CANCELLED

Render cancellation as terminal.

## 8. Human approval boundaries

Run-backed UI automation does not grant extra authority.

Automatic resume is allowed only while the run remains inside existing authority.

If a model/tool step requires Human confirmation, the UI must surface that decision rather than auto-approving it.

P1.5B Action Receipt and domain governance rules remain authoritative.

## 9. Conversation continuity

The current bounded session conversation history remains compatible input to run.start.

Once a run begins:

- the run persists its immutable input snapshot;
- resume does not depend on the browser resending that history;
- final successful reply may be appended to the visible chat transcript.

A later milestone may make the visible conversation itself a durable first-class object; P1.6A does not require that.

## 10. Progress presentation

P1.6A should provide useful but compact progress:

- working / paused / blocked / done;
- number of durable slices;
- latest safe activity label;
- optional elapsed time.

Avoid exposing raw internal chain-of-thought or model reasoning.

Tool observations may be represented through existing activity cards where appropriate.

## 11. Backpressure

The browser must not create uncontrolled resume loops.

Reference policy:

- only one resume request in flight for a run;
- stop on terminal state;
- stop on BLOCKED;
- use a bounded client-side maximum consecutive resumes before surfacing a recoverable “continue” control;
- Host remains the authority for concurrent-resume conflicts.

This is an experience guard, not a substitute for Host safety.

## 12. Compatibility fallback

During P1.6A migration:

- run-backed orchestration is the preferred/default path when the run actions are available;
- legacy `enterprise-agent.chat` may remain as an explicit compatibility fallback;
- fallback must not silently discard an already-created run;
- the same user message must not be executed through both paths.

## 13. P1.6A acceptance

P1.6A is complete when:

1. sending a Personal Agent message starts a durable run;
2. PAUSED slices resume automatically without Human slice management;
3. one visible Human message maps to one durable run;
4. terminal SUCCEEDED response appears as normal assistant chat output;
5. refresh/reconnect while PAUSED recovers the same run rather than creating a new one;
6. completed material WRITEs remain protected by Action Receipts;
7. BLOCKED is rendered as a Human decision/authority boundary;
8. no duplicate user message execution occurs during fallback/retry;
9. existing session conversation continuity remains compatible;
10. legacy synchronous chat remains available until run-backed production certification;
11. production smoke covers a read-only multi-slice task and one material-WRITE run;
12. UI changes are minimal: no manual run-management workflow is imposed on the Human.

## 14. P1.6 non-goals

P1.6A does not require:

- autonomous background execution with no client;
- distributed job scheduling;
- arbitrary Provider switching mid-run;
- durable multi-device conversation sync;
- exposing model private reasoning;
- removing all synchronous compatibility code immediately.

## 15. Next implementation step

Inspect the Eidos Personal Agent chat host integration and replace its primary send transport with run-backed orchestration behind a small adapter.

The adapter should be independently testable from visual rendering.

Start with deterministic interaction tests before changing presentation.
