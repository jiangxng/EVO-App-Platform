# P1.6 Run-backed Personal Agent Experience

**Status:** ACTIVE  
**Date:** 2026-09-28  
**Predecessor:** P1.5 Durable Agent Operations — COMPLETE

## 1. Goal

P1.5 made Personal Agent operations durable at the Host layer.

P1.6 makes that durability the normal product experience.

The current compatibility path still behaves conceptually as:

```text
send chat
→ one enterprise-agent.chat request
→ model/tool loop tries to finish inside that request
→ final reply
```

The target path is:

```text
send chat
→ enterprise-agent.run.start
→ receive runId + current durable state
→ bounded resume requests
→ reconnect/get by runId whenever needed
→ terminal reply / blocker
```

The Human should not have to understand the run protocol during ordinary chat.

## 2. Product invariant

```text
The conversation is the interaction surface.
The Agent Run is the execution lifetime.
The HTTP request is only one transport slice.
```

A browser tab, one fetch call, and one model loop must not be the durable unit of Agent work.

## 3. Scope

P1.6 is an interaction/experience migration over the already-proven P1.5C Host contract.

It must preserve:

- Person-first Personal Agent identity;
- current Context selection;
- bounded conversation-history semantics;
- Context Memory authority;
- P1.5A inventory semantics;
- P1.5B Action Receipt semantics;
- P1.5C run ownership/recovery;
- Human governance boundaries;
- current provider/model choice for a run.

## 4. Slice plan

### P1.6A — Run-backed Eidos chat transport

Goal:

Switch the Personal Agent send path to durable run actions without materially changing the visible chat experience.

Required behavior:

1. message send calls `enterprise-agent.run.start`;
2. client stores the returned `runId`;
3. if state is `PAUSED`, client advances using `enterprise-agent.run.resume`;
4. resume sends only `runId`, not the original task or prior tool state;
5. if state becomes `SUCCEEDED`, render final reply once;
6. current activities/tool observations remain renderable;
7. existing `enterprise-agent.chat` remains compatibility fallback behind an explicit migration boundary;
8. no duplicate conversation message is appended because of repeated get/resume rendering.

### P1.6B — Reconnect, progress and blocker experience

Goal:

Make durable run state visible enough to recover naturally after refresh/disconnect.

Required behavior:

- current active runId survives page refresh where appropriate;
- client calls `enterprise-agent.run.get` on reconnect;
- `PAUSED` can continue;
- `SUCCEEDED` restores final reply without re-execution;
- `BLOCKED` shows the real blocker and does not auto-cross Human authority;
- `FAILED` shows bounded failure evidence;
- Action Receipt references remain available for material WRITE evidence;
- user can distinguish “still working / can resume” from “finished” and “needs Human decision”.

### P1.6C — Compatibility migration and product certification

Goal:

Make run-backed execution the certified default Personal Agent path.

Acceptance:

- ordinary simple chat remains fast;
- multi-tool chat survives reconnect;
- one run containing a material WRITE does not repeat the WRITE after reconnect;
- new chat/session recovery does not depend on old browser in-memory state;
- domain authority still comes from domain READs, not run/receipt summaries;
- legacy synchronous chat fallback is observable and removable later, not silently mixed;
- no regression to P1.4X/P1.5A/P1.5B behavior.

## 5. Client state boundary

The browser may cache:

- current conversation presentation;
- current `runId`;
- most recent displayed run state.

The browser must not become authority for:

- whether a tool WRITE happened;
- whether a run is complete;
- current Proposal/Memory domain state;
- current Context authorization.

Those remain Host facts.

## 6. Resume cadence

P1.6A may automatically issue another resume request after a `PAUSED` response while the user remains on the page.

This is still bounded foreground continuation.

It must have:

- a client-side maximum consecutive resume count;
- no tight retry loop after errors;
- no automatic continuation from `BLOCKED`;
- no automatic retry of indeterminate WRITEs;
- clear stop on terminal state.

Background worker/autonomous scheduling remains out of scope.

## 7. Conversation-history relationship

Conversation history and run state remain separate.

For a newly started run:

- bounded prior conversation history may be supplied once as immutable run input.

For resume:

- prior history is not resubmitted;
- original user input is not resubmitted;
- durable run observations are reconstructed by the Host.

After a terminal reply:

- the normal conversation surface may append Human message + Assistant reply for subsequent turns.

## 8. Activities and tool evidence

Existing activity cards should be derived from durable run observations where practical.

A resumed run must not fabricate a second activity for an already-recorded WRITE merely because the UI re-rendered.

Where an observation contains an Action Receipt:

- receipt state is execution evidence;
- domain object cards/readback remain domain authority.

## 9. Compatibility strategy

Do not remove `enterprise-agent.chat` at the beginning of P1.6.

Use an explicit switch/fallback boundary so:

- run-backed chat can be tested against the existing path;
- rollback is possible;
- current UI remains usable if a run transport defect is found.

Once P1.6C passes, synchronous chat can be marked compatibility-deprecated.

## 10. P1.6A machine acceptance

P1.6A is machine-complete only when tests prove:

1. send starts a run;
2. PAUSED automatically advances with runId only;
3. terminal reply is rendered once;
4. reconnect calls get before deciding whether to resume;
5. SUCCEEDED reconnect does not call resume;
6. BLOCKED reconnect does not call resume;
7. failed resume does not tight-loop;
8. bounded continuation cap is enforced;
9. activity/tool observations survive rerender;
10. material WRITE receipt refs survive UI transport;
11. legacy chat fallback remains test-covered.

## 11. Human boundary

P1.6 introduces visible interaction behavior, so final P1.6C product certification may need Human UX judgment.

However, all deterministic transport/reconnect/idempotency tests should be completed automatically before involving the Human.

## 12. Current next step

Implement P1.6A by changing the Personal Agent Eidos chat transport/controller, not by weakening P1.5C run contracts.

The first implementation should keep visible chat behavior as close as possible to the current experience while replacing the execution transport underneath.
