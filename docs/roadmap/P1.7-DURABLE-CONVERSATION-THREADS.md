# P1.7 Durable Conversation Threads

**Status:** ACTIVE  
**Date:** 2026-09-28  
**Predecessor:** P1.6 Run-backed Personal Agent Experience Integration — VERIFIED PASS

## 1. Goal

P1.6 made Personal Agent execution durable.

P1.7 makes the visible conversation itself durable.

Today:

```text
Agent Run
= durable

Action Receipt
= durable

Context Memory
= durable

visible Chat transcript
= session-local
```

P1.7 removes that last discourse-continuity dependency on browser memory.

## 2. Core invariant

```text
Conversation Thread
= durable discourse

Context Memory
= governed durable knowledge

These are not the same thing.
```

A conversation message may contain:

- questions;
- tentative statements;
- errors;
- rejected ideas;
- temporary instructions;
- model explanations.

Those must not become durable knowledge merely because the thread is durable.

Promotion into Context Memory still requires the existing governed Proposal/Review path.

## 3. Target world model

```text
Human
  └── Personal Agent
        ├── Durable Conversation Thread
        │     ├── user turn
        │     │     └── Agent Run
        │     │            ├── tool observations
        │     │            └── Action Receipts
        │     └── assistant terminal reply
        │
        ├── Personal Context Memory
        └── authorized Enterprise Context Memory
```

## 4. Thread identity

Each thread has immutable identity facts:

- `threadId`;
- owner Principal subject;
- Principal actor type;
- active Context at creation;
- createdAt;
- optional title/label metadata.

The Host generates `threadId`.

The browser must not be able to forge ownership or Context scope.

## 5. Message model

Messages are append-only events.

Minimum durable message facts:

- `messageId`;
- `threadId`;
- role: `USER | ASSISTANT | SYSTEM`;
- content;
- createdAt;
- optional `runId`;
- optional reply-to message ID;
- optional structured presentation payload for assistant output.

Do not persist hidden chain-of-thought.

## 6. Run binding

One user turn may start one durable Agent Run.

Reference relationship:

```text
user message
  └── runId

run terminal SUCCEEDED
  └── assistant message
        └── same runId
```

The run remains the execution authority.

The thread remains the discourse authority.

Action Receipt remains the WRITE execution authority.

## 7. Host-built conversation history

For a thread-backed turn, the Host builds bounded model conversation history from durable thread messages.

The browser should no longer have to resend `conversationHistory`.

Rules:

- preserve newest relevant user/assistant discourse;
- keep the existing message/character budgets initially;
- ignore tool/internal event payloads unless rendered as explicit assistant discourse;
- never substitute Context Memory for conversation history;
- never substitute conversation history for Context Memory.

## 8. P1.7A — Thread foundation

Implement first:

### Contracts

`ConversationThreadV010`

`ConversationMessageV010`

`ConversationThreadStoreV010`

### Persistence

Reference append-only JSONL.

Default sibling path:

```text
conversation-threads.jsonl
```

Optional override:

```text
APP_PLATFORM_CONVERSATION_THREAD_FILE
```

### Host actions

Initial READ/management boundary:

```text
enterprise-agent.thread.create
enterprise-agent.thread.get
enterprise-agent.thread.list
```

Thread message append remains Host-internal in the first slice unless an explicit public action is needed by the run-backed interaction contract.

## 9. P1.7A acceptance

P1.7A is complete when:

1. threadId is durable and Host-generated;
2. thread Principal/Context ownership is immutable;
3. thread get/list are scoped to current Principal + active Context;
4. message events are append-only;
5. stable message IDs exist;
6. user and assistant messages can link to runId;
7. file-backed state reconstructs after process restart;
8. Host can derive bounded conversation history from thread messages;
9. Context Memory is not written by thread persistence;
10. no browser-supplied history is required to read/reconstruct a thread.

## 10. P1.7B — Thread-backed Agent turn

After P1.7A contracts stabilize:

```text
thread.send
→ append USER message
→ start Agent Run using Host-built thread history
→ run reaches SUCCEEDED
→ append ASSISTANT message linked to runId
```

Resume/reconnect must not append duplicate assistant messages.

Material WRITEs remain protected by P1.5B receipts.

## 11. P1.7C — Eidos durable transcript

Eidos should eventually:

- keep `threadId` as interaction identity;
- load transcript from Host;
- refresh/reconnect without losing prior visible messages;
- send a new turn against the existing thread;
- preserve the same chat UX;
- never require the Human to manage run IDs.

## 12. Ordering

Implementation order:

```text
P1.7A
Thread contracts + append-only store + scoped READ + history projection

→ P1.7B
Thread send + Agent Run binding + exactly-once assistant append

→ P1.7C
Eidos transcript recovery and thread-backed send
```

Do not jump directly to UI persistence before Host thread authority exists.

## 13. Conversation versus Memory

Examples:

### Durable thread only

```text
Human: “Maybe we should change the cutoff to 18:00.”
```

This is discourse, not a fact.

### Context Memory candidate

```text
Human: “From now on the warehouse normally cuts off at 18:00. Remember this.”
```

This may stage a Memory Proposal through the existing governed path.

The durable thread itself still does not create Memory.

## 14. Retention / privacy posture

Conversation threads may contain sensitive discourse.

P1.7A should keep scope narrow:

- current Principal;
- current active Context;
- Host-owned storage;
- no cross-Context enumeration.

Formal retention/deletion policy for conversation history can be a later slice.

Do not reuse Context Memory retention semantics automatically; the data classes are different.

## 15. Compatibility

During P1.7 migration:

- current run-backed chat remains functional;
- session-local `conversationHistory` remains compatibility input;
- thread-backed flows should prefer Host-built history;
- do not remove compatibility until thread-backed experience is certified.

## 16. Non-goals

P1.7A does not require:

- multi-device real-time sync;
- collaborative shared threads;
- semantic search over all conversations;
- automatic Memory extraction from every message;
- exposing internal chain-of-thought;
- arbitrary cross-Context thread moves.
