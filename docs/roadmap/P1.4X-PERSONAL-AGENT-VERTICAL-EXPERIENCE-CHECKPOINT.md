# P1.4X Personal Agent Vertical Experience Checkpoint

**Status:** MACHINE_VERIFIED — ready for Human browser experience  
**Date:** 2026-09-27

This checkpoint is a deliberate Human product review after P1.4A–P1.4E.

It uses the same production Package lifecycle, Eidos contracts, Provider resolution, Host Secrets, Principal/Context authority, Memory Proposal review, Memory governance and ActionHost paths as the product.

There is no demo-only page, fake Ready state, fake Memory or browser-owned Secret.

## 1. What is different from P1.3.1

P1.3.1 proved:

```text
Install
→ Provider setup
→ Ready
→ Personal Agent
→ Memory Review / Governance / Source Health
```

P1.4X extends the Human-visible lifecycle through:

```text
Install
→ Provider setup
→ Ready
→ Personal Agent
→ Memory Proposal
→ Human Review + Accept
→ Memory Governance
→ Retention Preview / Commit
→ Memory Quality
→ Human Quality Evaluation
→ Contradiction Resolution
→ Personal Agent Follow-up
→ Agent continues from the Follow-up
```

The purpose is product judgment, not another backend milestone.

## 2. One-command local experience profile

From a clean/current `main` checkout:

```powershell
git pull
npm ci
npm run experience:start
```

Open:

```text
http://localhost:4100
```

The console prints:

- the browser URL;
- the local Human subject;
- the durable local state file;
- the **Administrator authorization** value used only when the browser asks to change a Host Secret.

Default local Administrator authorization:

```text
local-experience-admin
```

The launcher configures only formal Host deployment inputs:

- Host Static Session Provider;
- Host Static Authorization Provider;
- bootstrap administrator authentication;
- durable App Platform state.

It does **not**:

- install Personal Agent;
- install OpenAI Provider;
- configure an API Key;
- create Memory;
- create quality evidence;
- create contradictions;
- create Follow-ups.

Those must happen through the real product lifecycle.

### Start clean

To delete only the dedicated local experience state:

```powershell
npm run experience:reset
npm run experience:start
```

Do not use `experience:reset` against a production state path.

## 4. Install and configure the real LLM Provider

In Personal Agent Setup:

1. **LLM Provider** → **Open Provider catalog**.
2. Install **OpenAI LLM Provider**.
3. Return to Personal Agent → **Set up**.
4. **Provider configuration** → **Configure Provider**.
5. Keep the default model/base URL unless you intentionally want another compatible model.
6. Paste a real OpenAI API Key into **API Key**.
7. In **Administrator authorization**, enter the value printed by `experience:start`:
   `local-experience-admin`.
8. Save.

Expected:

- Host Secrets Provider stores the API Key;
- the browser never reads the saved value back;
- Static Authorization Provider authorizes the bootstrap secret write;
- OpenAI Provider runtime refreshes;
- readiness is recomputed from the real Provider.

Do not put the API Key in source code or browser localStorage.

## 6. Create a real Memory Proposal

In Personal Agent, send:

```text
请把“仓库标准截单时间是 17:00”作为一个 FACT Memory Proposal 提出来让我审核。
不要直接写入持久 Memory；如果需要持久化，必须走 Proposal → Human Review。
```

Expected Agent behavior:

- uses the formal Memory Proposal tool;
- tells you it is pending review;
- does not claim durable Memory was already written.

Open:

```text
Personal Agent → Review Memory
```

Review the Proposal and **Accept** it.

PASS:

- acceptance requires Human confirmation;
- durable Memory appears only after acceptance;
- immutable provenance/attribution is preserved.

## 7. Create a real contradiction

Back in Personal Agent, send:

```text
先搜索当前 Context 的 Memory，找到关于“仓库标准截单时间”的现有记录。
然后提出一个新的 FACT Memory Proposal：“仓库标准截单时间是 18:00”。
如果它与 17:00 的现有 Memory 冲突，把那条现有 Memory 的 ID 放入 potentialContradictionMemoryIds。
不要修改旧 Memory，也不要替我决定哪一条是真的。
```

Open **Review Memory**, inspect the contradiction signal, and Accept the new Proposal.

Then open:

```text
Memory → Memory Quality → Review contradictions
```

PASS:

- both Memory records remain immutable;
- an OPEN contradiction exists in the quality overlay;
- no model/provider automatically decides truth.

## 8. Resolve contradiction and observe Follow-up

In **Memory Contradictions**, choose a Human resolution.

For the first checkpoint, `BOTH_VALID` is useful if you imagine the two cut-off times apply under different conditions.

Add a reason such as:

```text
可能适用于不同仓库、日期或业务条件，需要进一步补充上下文。
```

Confirm.

Then open:

```text
Personal Agent → Personal Agent Follow-ups
```

Expected:

- contradiction is RESOLVED;
- original Memory records are unchanged;
- an OPEN planning-only Follow-up exists;
- opening Personal Agent shows the Follow-up as a suggested prompt;
- the Agent can read it with `personal_follow_up_list`;
- it still cannot rewrite Memory without a new Proposal/review cycle.

This is the key P1.4E vertical closure.

## Human browser finding — session conversation continuity

The Human checkpoint exposed a distinct layer between Chat UI state and Context Memory.

Observed failure:

```text
Turn N:
Agent reads two duplicate 17:00 Memory records
→ explains the duplicate

Turn N+1:
Human: "这个重复问题你判断怎么处理更合适..."
→ Host received only Turn N+1 text
→ Agent could not resolve "这个"
→ broad platform discovery
→ maxSteps exhausted
```

Root cause:

- Eidos kept the visible transcript in browser state;
- `enterprise-agent.chat` submitted only the newest composer message;
- Agent model input therefore had no prior discourse context.

P1.4X now distinguishes:

```text
Conversation History
= session-local discourse continuity
= helps resolve "this / that / continue / what we just discussed"
= not authoritative
= not durable

Context Memory
= governed durable knowledge
= cross-session / cross-deployment continuity
= Human-reviewed when required

Host READ
= current authoritative platform state
```

Implementation boundary:

- Eidos Chat v0.2 sends only prior `user` / `assistant` discourse;
- error/system rows and operational evidence/activity cards are not promoted into authority;
- maximum 16 messages;
- maximum 8,000 characters per message;
- maximum 24,000 characters total;
- Host independently validates the same limits and roles;
- history is preserved through every tool step;
- provider-backed model receives history before the current user turn;
- system instruction explicitly requires Host READ for current state and Context Memory for durable knowledge.

This is intentionally **session continuity**, not chat-history persistence. Cross-refresh durable conversation storage remains a separate future product decision.
