# P1.8 Conversation Lifecycle & Retention

**Status:** ACTIVE — P1.8A VERIFIED / P1.8B 90-DAY POLICY LIVE PASS / P1.8C IMPLEMENTATION READY  
**Date:** 2026-09-28  
**Predecessor:** P1.7 Durable Conversation Threads — VERIFIED PASS

## 1. Why P1.8 exists

P1.7 made Personal Agent conversation discourse durable Host state.

That solved refresh/reconnect continuity, but introduced the next responsibility:

```text
durable conversation
without lifecycle/retention
= unbounded sensitive state
```

P1.8 makes conversation lifetime explicit.

## 2. Core invariant

```text
Conversation lifecycle is Host governance over durable discourse.
It is not Context Memory governance.
```

Conversation threads may contain tentative ideas, mistakes and temporary instructions. They remain discourse even when archived or retained.

## 3. Slice plan

### P1.8A — Thread lifecycle foundation

Introduce append-only lifecycle state:

```text
ACTIVE
→ ARCHIVED
```

Rules:

- new thread starts ACTIVE;
- archive appends a lifecycle event;
- archive never rewrites/deletes messages;
- archived thread remains exact-ID readable;
- default list excludes archived;
- explicit `includeArchived=true` includes archived;
- new Agent turns on archived threads fail closed;
- Host Principal + active Context scope is rechecked;
- Context Memory receives no side effect.

### P1.8B — Retention policy

Add conversation-specific retention semantics.

Required direction:

- policy separate from Context Memory retention;
- preview before destructive cleanup;
- auditable eligibility decision;
- explicit Human authorization for irreversible purge;
- protected/legal-hold posture can follow later;
- thread/message purge must never silently delete Context Memory or Action Receipt/Run audit evidence.

### P1.8C — Eidos thread management

Expose normal product semantics:

- New Chat creates a fresh durable thread;
- recent thread history;
- switch/reopen a thread;
- archive a thread;
- selected thread survives refresh;
- archived thread is read-only unless a future explicit restore contract is added;
- no accidental prior-thread discourse enters a New Chat.

## 4. P1.8A contract

Conversation Thread materialization adds:

```text
state: ACTIVE | ARCHIVED
archivedAt?
archivedBySubjectId?
```

Append-only event:

```text
THREAD_ARCHIVED
```

The event contains:

- threadId;
- archivedAt;
- archivedBySubjectId.

A second archive is idempotent and does not add another lifecycle event.

## 5. Listing semantics

Default:

```text
thread.list
→ ACTIVE only
```

Explicit governance/history view:

```text
thread.list(includeArchived=true)
→ ACTIVE + ARCHIVED
```

Exact:

```text
thread.get(threadId)
→ returns scoped archived thread too
```

Archive is therefore not deletion.

## 6. Send semantics

```text
thread.send(ARCHIVED)
→ CONVERSATION_THREAD_ARCHIVED
```

The rejection happens before:

- LLM Provider resolution;
- Agent Run creation;
- tool execution.

This prevents a new execution from being attached to closed discourse.

## 7. Scope and authority

Archive action:

```text
enterprise-agent.thread.archive
```

The Host resolves Principal + active Context.

The client cannot archive another Principal/Context thread by supplying a forged threadId.

## 8. Persistence

Lifecycle events use the existing append-only Conversation Thread event store.

File-backed runtime remains:

```text
conversation-threads.jsonl
```

No separate mutable lifecycle database is introduced.

## 9. P1.8A acceptance

P1.8A passes when:

1. new thread materializes ACTIVE;
2. archive appends THREAD_ARCHIVED;
3. messages remain immutable/readable;
4. second archive is idempotent;
5. default list excludes archived;
6. includeArchived=true returns archived;
7. exact get returns archived;
8. thread.send rejects archived before run creation;
9. history projection remains readable;
10. file-backed restart preserves archive state;
11. current Principal + Context scope remains enforced;
12. Context Memory has no side effect.

## 10. Non-goals

P1.8A does not yet implement:

- physical deletion;
- restore/unarchive;
- retention schedules;
- archive UI;
- thread title editing;
- shared/collaborative threads.

Those remain later P1.8 slices.

## 13. Human retention policy decision — 90 days

The Human product owner selected:

```text
retainArchivedForDays = 90
```

Decision semantics:

- applies only to `ARCHIVED` Conversation Threads;
- retention clock starts at immutable `archivedAt`;
- `ACTIVE` threads are never purge-eligible;
- the 90-day decision establishes retention policy only;
- it does **not** authorize any destructive purge;
- irreversible deletion/tombstone execution remains a separate Human authority boundary.

Runtime direction:

```text
effective policy read
→ 90 days

retention preview without override
→ uses 90 days

retention preview with explicit override
→ simulation only

destructive purge
→ disabled
```

Production configuration should explicitly set:

```text
APP_PLATFORM_CONVERSATION_RETENTION_DAYS=90
```

The code default is also 90 days so the Human-selected product policy remains deterministic if deployment configuration is absent, while the policy read surface records whether the effective source is explicit platform configuration or the Human platform default.

### Secure erasure remains separate

The current append-only Conversation Thread JSONL contains message content directly.

Therefore a logical `THREAD_PURGED` tombstone would **not** prove that sensitive message bytes were physically erased.

Do not claim irreversible deletion until the storage model supports real physical or cryptographic erasure plus audit evidence that does not itself retain the erased content.

This remains a separate Human-authorized security boundary.

## 15. P1.8C active gate — Eidos thread management

P1.8C now owns product thread lifecycle UX:

```text
New Chat
→ fresh durable threadId
→ no prior-thread history

History
→ Host thread.list

Switch
→ Host thread.get
→ render durable transcript

Archive
→ Host thread.archive

Refresh / re-mount
→ restore selected durable thread
```

Acceptance:

1. New Chat creates a new durable thread identity.
2. No previous thread discourse enters the new thread.
3. History comes from current Principal + active Context Host list.
4. Switching loads the selected Host transcript.
5. Archived threads may be reopened read-only.
6. Archived thread send remains rejected by Host.
7. Archive is an explicit scoped Host action.
8. Selected thread survives refresh/re-mount.
9. Browser `conversationHistory` never becomes authority again.
10. Conversation management has no Context Memory side effect.
