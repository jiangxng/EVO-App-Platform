# EVO 项目交付开发工作流（项目级 CURRENT_AUTHORITY）

Status: CURRENT_AUTHORITY / accepted by project owner 2026-10-14
Scope: EVO-App-Platform 全部开发工作线；跨仓变更按各仓 owner 的契约协调。本规范约束项目的开发过程，不代表任何既有 PR 自动验收或生产发布授权。

## 1. 核心原则

**以可用、可测试、可合并的功能闭环作为交付单位，不用分支数、PR数、研究次数或截图数代替进展。**

1. **已验证能力契约优先**：开发前检查最新 main、已有 PR、历史验证、公共接口和相关模块测试。可复用的稳定能力直接复用；不因新聊天、换窗口或更换模型重新做已完成的研究/实现。只有涉及接口语义变更、安全/授权边界、异常数据、生产风险或相关回归失败时才定向深入旧实现。
2. **同一任务一条活动开发主线**：一项可独立交付的功能闭环原则上对应一个活动分支和一个 PR，允许在同一 PR 里多次提交、修复和运行 CI。禁止为每个函数、微小实验或验收条目反复创建分支。不同 owner 之间真正独立且不存在共享文件冲突的工作，可以短期并行，但必须有明确的集成顺序和退出条件。
3. **大阶段不等于永久分支**：PA-02、2D等里程碑可以由多个**依次完成**的短闭环 PR 组成。一个 PR 达到闭环后先合并 main，再从最新 main 开始下一个工作分支；不得使主分支长期落后或积累多个开放子分支。
4. **开发中发现冲突就在原 PR 收敛**：继续提交到既有分支并更新既有 PR，正常合并 main、修复冲突、重跑受影响 CI。禁止通过创建替代 PR、重写历史、跳过分支保护来规避冲突/门禁。
5. **及时合并和清理是同一项交付责任**：CI合格、关键影响检查完成、代码具备确定性回归后尽早合入 main。核对 PR 的 merged、最终 commit SHA、独有内容是否安全进入 main，删除不再使用的过程分支；有独有提交、来源未明、仍被 PR 使用或受到保护时仅报告、不得删除。
6. **验证分级，不重复验证劳动**：CI 可以对已验证契约持续回归；但不重复实现和研究。以变更影响选择定向单测/集成/安全/契约检查；变更共享 Host/企业 WRITE/Principal 或跨租户权限则增加相应安全和恢复验证。测试绿不等于实际部署或所有 Human 体验均已证明。
7. **轻量 Host、插件 owner 与生产门禁保持**：共享基础文件可以在已授权范围内修改，但不得把可选实验功能默认变为生产运行逻辑。正式部署、数据迁移及不可逆动作仍遵守单独授权；不得为了提前宣布完成而跳过权限、双重写入防护、未知结果核验。
8. **交接必须可续接**：记录当前 main、唯一活动 PR/分支、已验证且无需重做的能力、尚未关闭的原始验收 gate、最新 CI 及合并状态。不同聊天窗口按仓库事实接续，非生产阶段不得把部署验收擅自加入开发门槛。

## 2. 每个闭环的验收账

| 时点 | 必须核实 |
| --- | --- |
| 开始 | 目标与完成条件、复用合同与现有测试、是否已有相同任务/PR |
| 开发 | 相同分支反复提交，新改动的影响范围与失败恢复；不补无关功能 |
| 合并前 | 相关 CI + 安全门禁通过；main 差异已对齐；没有覆盖其他窗口有效修改 |
| 合并后 | PR merged、SHA、main 中代码可用、源分支已删除或记录未清理理由 |
| 阶段收口 | 逐项检查原定业务能力/集成 gate，明确 DEV_COMPLETE / PRODUCTION_READY / DEPLOYED 不同证据 |

## 3. 例外与执行

- 独立并行 PR 必须注明 owner、可独立集成原因、共享文件冲突预防和预期合并顺序。默认不开长期并行分支；不是所有并行都要被强行合成一个巨型 PR。
- 历史未合并分支只做差异吸收或有证据的归档，不因“只剩一个分支”的目标丢弃独有代码。
- 若发现一个交付过大、合并风险增加，应先在原 PR 完成最小安全闭环并合入，余下任务从新的 main 继续。不得将安全相关改动人为拆成无法核验的碎片。
- 仓库已有的 `.github/workflows/branch-hygiene.yml` 负责 Agent 分支检测及部分精确安全清理；本规范对全部项目线生效，但不得假称其他 owner 的自动强制门禁均已部署。
- 执行文件 `AI-BOOTSTRAP.md` 和 `LLM.md` 必须指向本规则；Agent 专项补充见 `docs/agent-line/AGENT-DELIVERY-AND-BRANCH-GOVERNANCE.md`。若专项历史快照和本规则冲突，以本规则及最新仓库实际状态为准。

## 4. 快速反馈、止损换路线（2026-10-21 执行补充）

项目负责人确认：后续交付统一采用“先测差距与备选路线 → 同根因问题批量修复 → 最小有效验证 → 最终 HEAD 完整 CI → 真实验收”的工作方式，并且不得在两轮无有效进展时继续无证据地堆补丁。执行细则、换路线触发条件、测试失败分类与 BEX-01 M06 首次应用，见 [《快速反馈与路线止损执行规程 v1.0》](../governance/FAST-FEEDBACK-AND-ROUTE-PIVOT-v1.0.md)。

该执行规程**不新增全项目强制 CI、不降低既有安全/权限/Human/生产门禁**。新窗口已经通过 `AI-BOOTSTRAP.md` 必读本文件，应同时按此补充规程执行。规则属于持续优化的开发方法，不改变历史已签收结论。
