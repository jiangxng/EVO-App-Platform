# Platform Secrets v0.1

**Status:** P0 implementation  
**Date:** 2026-09-26  
**Authority:** EVO App Platform  
**Scope:** Package-declared Secret requirements, Host Secrets Provider, Workbench credential configuration and Provider runtime resolution.

## 1. Purpose

Secrets are credentials or sensitive values that must not be stored as ordinary Package Settings, Package Manifest content, source constants, browser-readable state, Help content or logs.

P0 establishes one generic boundary:

```text
Package declaration
  ↓
Eidos Settings presentation
  ↓
Host administration authorization
  ↓
Managed Secrets Provider
  ↓
encrypted Secret store
  ↓
secrets.resolve
  ↓
Provider/runtime consumer
```

OpenAI API credentials are the first production consumer. The contract is vendor-neutral.

## 2. Package declaration

A Package may declare required Secrets in `PackageManifestV010.secrets`.

A declaration contains metadata only:

```text
key
label
description?
scope
required?
```

It MUST NOT contain a Secret value, default credential, token, password, private key or encrypted payload.

The declaration says what the Package needs; the Host decides how the value is collected, stored, authorized and resolved.

## 3. Public Secrets contract

The public platform contract uses:

- `SecretReferenceV010`
- `SecretDescriptorV010`
- `SecretsResolverV010`
- `ManagedSecretsProviderV010`

The replaceable capability is:

```text
secrets.resolve
```

Consumers depend on that capability, not on filesystem paths, Railway variables, KMS vendors or database tables.

A Secret reference is identified by:

```text
namespace
key
scope
scopeId?
```

P0 uses the Package ID as the namespace.

## 4. Reference Provider

The first implementation is:

```text
Package: host-encrypted-secrets-provider
Provider: host.encrypted-secrets
Capability: secrets.resolve
```

It is a first-party Host Provider and is installed as a platform foundation.

The P0 encrypted file store uses:

- AES-256-GCM;
- random 96-bit IV per write;
- authenticated additional data derived from Secret identity;
- a random 256-bit Host master key;
- separate master-key and encrypted-state files;
- restricted file permissions when supported by the OS.

The master key is generated by the Host when the persistent Secret boundary is first initialized. It is not a Package secret and is not supplied to plugins.

## 5. Production persistence

The encrypted Secret state and its Host master-key file must live on durable Host storage.

When `APP_PLATFORM_STATE_FILE` points into a persistent state directory, P0 defaults to colocating:

```text
secrets.enc.json
secrets.master.key
secret-audit.jsonl
```

with the lifecycle state directory.

A container deployment without durable storage may use the in-memory Secret store only for development/testing. It MUST NOT be described as production-persistent Secret management.

Long term, the same `secrets.resolve` contract may be backed by Vault, AWS Secrets Manager/KMS, Azure Key Vault, GCP Secret Manager or an enterprise-owned Provider.

## 6. Workbench configuration

Human configuration is rendered only through Eidos public capabilities.

For a Package that declares both ordinary settings and Secrets, App Platform composes one Eidos `settings-editor` surface:

```text
ordinary settings
  model
  baseUrl

Host-managed credential
  API Key              [password input]
  API Key status       Configured / Not configured
  Remove API Key       [boolean when configured]

bootstrap admin auth    [temporary secret input]
```

Rules:

- the input is blank whenever the page loads;
- an existing Secret is never sent back to the browser;
- blank input means keep the existing Secret;
- a non-empty input replaces it;
- explicit Remove deletes it;
- ordinary settings continue to use `SettingsStore`;
- Secret fields never enter `SettingsStore`.

The visual implementation belongs to Eidos Productive Design Language. App Platform does not create a parallel credentials UI.

## 7. Authorization

Secret mutation is a privileged Host administration operation.

P0 action:

```text
secret.value.manage
```

The current bootstrap phase authenticates `bootstrap-admin`; authorization is still decided by the active `authorization.check` Provider.

Missing authentication, missing/ambiguous authorization Provider, policy denial or Provider failure fails closed.

The temporary bootstrap credential is not a substitute for the planned Identity/Session/Principal boundary.

## 8. Audit

Secret write/remove operations emit non-secret audit records.

Allowed audit material:

```text
event id
timestamp
actor
policy Provider
correlation id
Secret namespace/key/scope
operation
outcome
reason
```

Forbidden audit material:

- Secret value;
- authorization credential;
- plaintext token;
- decrypted payload.

## 9. OpenAI migration

The OpenAI Package declares:

```text
namespace: openai-llm-provider
key: apiKey
scope: INSTALLATION
```

The OpenAI runtime resolves that reference through `secrets.resolve`.

`OPENAI_API_KEY` remains a temporary compatibility migration source only:

1. if the Host Secret is absent;
2. and a legacy environment value exists;
3. the Host migrates it into the Secrets Provider;
4. runtime execution then prefers the Secrets Provider.

New configuration MUST use Workbench/Secrets rather than Railway environment variables.

Model ID and API Base URL remain ordinary non-secret Settings.

## 10. Lifecycle

A Package may require `secrets.resolve` as a Capability dependency.

For the OpenAI Package, installing it also installs/activates the first-party Host Secrets Provider when needed.

Disabling or uninstalling the consuming Package does not automatically delete its Secret. Secret deletion is an explicit administration action so accidental lifecycle operations do not destroy credentials.

Future retention policy may make this configurable, but silent deletion is not P0 behavior.

## 11. Security constraints

P0 MUST preserve:

- no plaintext Secret in Manifest;
- no plaintext Secret in SettingsStore;
- no plaintext Secret in API response after save;
- no plaintext Secret in audit/logging;
- no browser readback of stored Secret;
- server-side authorization for mutation;
- deterministic scope identity;
- encrypted persistent storage;
- Provider-neutral resolution contract.

A password-type input by itself is not a Secret boundary.

## 12. CI

Secrets Provider CI validates:

- encrypted persistence and reload;
- no plaintext in state/key files;
- metadata never includes values;
- scope fail-closed behavior;
- Package dependency on `secrets.resolve`;
- Settings UI does not persist Secret values;
- portable Plugin Protocol Secret declarations.

Platform CI validates integration with App Manager, Eidos Settings, Provider resolution and existing platform invariants.

## 13. P0 completion

Secrets P0 is complete when:

```text
install OpenAI Provider
→ Host Secrets Provider dependency is active
→ Settings shows API Key as an Eidos secret field
→ saved API Key is never returned
→ encrypted persistent store contains no plaintext
→ OpenAI runtime resolves API Key through secrets.resolve
→ changing the Secret does not require a service redeploy
→ ordinary model/baseUrl Settings still work
→ removing the Secret makes OpenAI runtime unavailable
→ CI and Help describe the same behavior
```

Identity/Session remains the next security maturity layer for replacing bootstrap administration authentication.
