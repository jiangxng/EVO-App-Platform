# EVO 快速反馈与路线止损执行规程 v1.0

Status: LIVING_RUNBOOK / 项目负责人 2026-10-21 明确要求优化开发节奏并持续沿用。  
Authority: [项目级交付开发工作流](../architecture/DEVELOPMENT-DELIVERY-WORKFLOW-v1.0.md) 的执行补充；不取代现有架构、质量、权限、Human 或生产门禁。  
Scope: EVO-App-Platform 后续功能/UI/治理交付；跨仓协作须遵从对应 owner、Eidos 契约及既有分支约束。  
Adoption: 独立文档 PR 未合并前作为当前工作线的试行规则；合入 main 后作为 fresh session 可发现的常规执行规则。

## 0. 目标与不可妥协项

**缩短“明确差距 → 真实可用 → 可签收”的周期，不以提交次数、CI 运行次数、文档字数或截图数量冒充产品进度。**

- **保持**：真实 Host/Eidos 产品行为、权限和安全、合同约束、必要的回归测试、CI、Human 视觉签收、生产/真实数据另行授权。
- **削减**：无效重复研究、小改动连续远程推送、测试脚本自身问题导致的整套回归、同一批问题拆成多个 PR、已决事项反复写长交接。
- **禁止**：为了提速跳过失败、把 mock 当真实产品、降级原始 100% 视觉目标、在无证据时宣称 PASS、向 main/生产直接写入以绕过门禁。
- **判断效率**：优先看本轮关闭了哪些真实差距、留下多少开放 gate，技术提交与 CI 次数只用作诊断。

## 1. 开始前的轻量工作卡（不另外开审批会）

每个可交付闭环用下列 7 行以内信息作为当前 PR 描述或工作备注；复用已有交接内容，不新建冗长模板：

| 栏位 | 最小记录 |
| --- | --- |
| 目标 | 用户能真实完成什么；原始验收标准不变 |
| 现状 | 最新 main、活动 PR/owner、已 PASS、剩余 OPEN、不可重复动作 |
| 证据 | 现有原型/产品截图、真实日志/测试或接口契约；标注来源 |
| 方案 | 首选路线、至少一个可行备选或不采用的理由；简单改动无需形式化比选 |
| 可测差距 | 改前基准和改后预期，含失败/恢复路径 |
| 边界 | 涉及的模块/文件、并行 owner、权限/真实数据/Human 门禁 |
| 退出 | 哪些证据足以完成本闭环；什么现象要求停下改路线 |

已证明的能力不重做研究。源码、运行时和最新 PR 与旧聊天不一致时，以现时权威事实为准。

## 2. 五步快速交付闭环

1. **先量差距，再选路径。** 在已有体验/基准上一次性识别相关问题，找共同根因和共享改动点；对有风险的路径快速比较 2 个选项，写出为什么选择当前方案、何时放弃。
2. **把相邻问题合成一批。** 原则上一个活动分支/PR、一个可核验闭环；UI 相近且共享根因的约 3–5 个差距可合批（这是指导值，不是硬指标），避免只修 1px 就开启一个新 PR；有不同 owner/权限/安全边界则拆开。
3. **最便宜的有效验证优先。** 改前记录可复现基线；改后优先编译/类型、变更影响相关单测与契约、目标页面或目标端到端断言、必要的人眼截图核对。若不能在本地可靠运行，明确写出环境限制，利用最小可用远程门禁，不能谎称已在本地 PASS。
4. **阶段性推送、完整门禁。** 合理集中相关修复后推送同一分支；远程强制 CI 按现有规则正常执行，不能删除或屏蔽。每次失败先分类、定位，再修复；正式交付以**精确最终 HEAD** 完整相关 CI、真实产品证据为准。
5. **对照原始目标关闭差距。** 记录实测数字/截图/可复现行为、残余差距、Human 仍需决定的事项；该合并的短闭环及时合并，清理安全可删的过程分支。DEV_COMPLETE、MERGED、DEPLOYED、HUMAN_PASS 不互相替代。

## 3. 强制“不要一条路走到黑”机制

满足下面任一条件，**暂停继续堆同类补丁**，先做一次短复盘并选择继续、回退、改路或拆分：

- **两轮连续尝试后核心指标不改善**，或没有新增定位证据；第三轮前必须重新查看真实 DOM/布局、数据流或最小复现，明确替代方案。
- **两轮 CI 失败均源于测试脚本/选择器/环境，而非产品变更**：先修测试基础设施或采用更小的稳定复现，再继续产品工作；不要把测试误报当产品问题硬修。
- **改动触及原先未预期的公共契约、授权、持久化或并行 owner 文件**：先评估边界/风险，必要时将工作移交正确 owner 或单独契约 PR，而不是在页面里绕开平台。
- **实测与方案假设相反**（如 CSS 方案没有降低行高；视觉只改善一点却破坏可操作性）：立即验证根因，更换路线；保留失败证据但不要保留无效补丁。
- **交付体积持续膨胀**、依赖 PR 长链阻挡集成，或需要 Human 改需求：重新划分可独立验收闭环，不擅自修改验收目标。
- **证据来源不足**：回到可观察的运行事实或标记阻塞，不继续凭推测叠加代码。

短复盘**只记四行**，不要求新文档或新的审批：
```text
假设：预计什么会改善？
事实：两轮实际观测了什么？失败属于产品/测试/环境/契约哪一类？
选择：继续 / 回退 / 换方案 / 拆 owner，及理由。
下一次验证：用哪个最小实验确认新假设？
```
复盘后可以继续原路线，但必须有新增证据和明确成功标准；不因“已投入很多”而继续盲目尝试。

## 4. 分层验证：少跑重复活，不降低质量

| 层级 | 触发时机 | 目的与要求 |
| --- | --- | --- |
| L0 静态/快速测试 | 实现过程中 | 类型/构建、直接关联的协议/单测；能低成本排错就不先推全仓 |
| L1 目标真实流程 | 一批改动形成可用闭环 | 针对性 Host/Eidos Chromium/集成、权限及状态持久化，证明真实行为 |
| L2 完整相关 CI | 正式 PR 准备交付及最终 HEAD | 运行仓库现有 required checks，不跳过、不用旧 SHA 代替 |
| L3 Human/生产门禁 | 原验收协议要求的对应阶段 | 视觉签收、真实业务操作、生产发布或真实数据必须分别取得相应授权 |

CI 强制自动运行是仓库事实；本规程**不承诺通过文字减少自动触发的 CI**。提升速度来自减少无效远程迭代、早发现测试问题、改善针对性测试和优化后续 CI 配置（如有必要须另开受控工程变更）。

失败先分类：**产品真实回归 / 测试实现错误 / CI 环境或偶发 / 权限或契约问题**。每类采用不同修复方向，禁止见红就改业务代码。

## 5. Human UI 和高保真任务的专用做法

**首要路径：先读有版本的原型源代码，再对照真实 Host；截图只作最终实际渲染与 Human 验收证据。** 如果设计有可读的 HTML/CSS/JS，先抓批准的原型精确 commit/blob，直接从原始 DOM/组件、CSS 颜色/布局/媒体查询和 JS 的事件/状态机提取目标。禁止继续通过截图反推已有源码的布局或追逐跨视口行高。原型没有源码时明确写明来源类型，才使用设计图/截图/可测视觉事实建立目标。

- **功能 100%**：逐项对应原型真实交互状态与 Host 真正可用的操作、未完成/错误/恢复、身份授权、合法保存/预检/提交；演示 localStorage/虚拟记录/假自动保存只提供交互意图，不是可移植的真实业务逻辑。
- **布局 100%**：按原型区域、阅读顺序、层次、控件排列、桌面/手机合理自适应比对；不追求任何分辨率的每行高度/间距/像素一模一样，不因降低触控与可访问性换取截屏好看。
- **颜色 100%**：提取原型真实 CSS 颜色/变量、状态与按钮色，核对对比度/主题语义，并映射既有 Eidos tokens/受控局部主题。原型与通用设计权威不一致时记录冲突交正确 owner，不得静默覆盖全局样式。
- 一次性以**功能 / 布局 / 颜色**三列列出所有真实剩余差距，区分源代码已定义、真实 Host 已等价、演示和授权语义冲突。合并共同根因实施，先最小 L0/L1 验证，最终 exact HEAD CI + L3 Human 认定；自动 Review Gate PASS != Human 100%。
- 同步查看相同状态的完整桌面/手机 Host 实测证据（常用 1280px、390px，或者项目实际约定的视口）；截图对比放在**实现后**，只用于捕捉运行时偏差、字体/断点异常、浏览器兼容和人工可用性问题。
- 对相近问题优先共同修复；保留语义、可访问性、44px 触控目标（适用处）、Eidos API 和真实业务交互；禁止“截图看起来一样”却损失真实功能。
- 每批提供**改前/改后**、实际行为测试、未修完的视觉差距。自动化 Human UI Review Gate PASS **不是** Human 本人视觉认可。
- 遇到 Eidos 与 Platform 职责分歧：先明确 Eidos 负责通用交互能力、Platform 负责 BEX 业务编排；不要在一个页面里硬编码通用框架缺口。

## 6. 并行开发、PR 和交接控制

- 复用现有活动分支/PR，避免每次失败另开一个补丁 PR；仅新工作线使用独立分支。不得覆写另一个窗口/owner 的共享文件或未经授权直接合并其工作。
- 原则上短闭环 PR → 通过验证 → 按现有授权合入 main → 下个闭环从最新 main 继续；已存在的 stacked Draft PR 先安全梳理，不强行改 base 或丢掉未合并改动。
- 每轮只更新**增量**结论、来源证据、替代路径和下一次真实 gate；研究材料保留原始 URL/查阅状态。已有资料不无故重新大规模整理。
- 进度报告用 4 个字段：**本轮关闭的真实差距；可核验的 PR/CI/截图；剩余开放差距与阻塞；下一条最小可交付路径**。总里程碑数字不变时可以独立显示差距关闭数，不伪造里程碑 PASS。

## 7. 换窗口不得丢失开发判断（ChatGPT / Codex / 多 Agent）

**启动入口负责发现规则；当前 owner PR/交接记录负责保存事实。两者缺一不可。** 新窗口必须先执行 `AI-BOOTSTRAP.md`，再读取本规程，不能只看上个窗口的口头摘要或最新提交标题。

### 上一窗口离开前（原 PR 中的小增量记录）

记录在**当前任务拥有者的 PR 描述/评论或原有专属交接文件**；不扩写全局 `project.status.json` 来容纳某个并行窗口的试验细节：

```text
当前基线：仓库 + 最新 main + owner PR/base/head SHA + 实际运行/CI/原型证据。
已关闭：哪些真实功能/视觉差距已证明、何种门禁仍未签收。
未关闭：按用户可见差距排列；下一批建议一起解决的共同根因。
失败与禁重试：本窗口试过什么（路径/提交/运行/观测）、为什么无效；区分产品/测试/环境。
替代与止损：首选下一次最小验证、至少一个真实备选、触发换路的事实条件。
边界：与哪些窗口/owner 并行、不可改哪些文件、真实数据/Human/生产授权边界。
```

没有失败实验时写 `无已记录失败路线`，而不是编造。已验证且没有变更的研究，引用原始索引，不再写一份新研究报告。只有当原工作没有现成 PR/交接载体时才创建最小独立记录。

### 新窗口第一次动手之前（短复述，防止重复）

1. 从仓库规范和准确 owner PR 取得**最新**状态，核对上一窗口交接提交与今天 main/PR 的差异。
2. 找到正在推进的 **真实用户差距**，不要用“继续修 CI/继续写文档”替代业务目标。
3. 复述**最后一个已知失败假设**和证据；如果已经试过两轮无改善，先改实验/路径，不得直接重复旧补丁。
4. 查验现有原型/代码/真实 Host 测试是否足够；优先做最小可辨别实验，再集中修改，最后完整相关 CI。
5. 本轮完成后，把**新的事实/决策/剩余问题**写回**同一 owner PR/交接**；不要因换聊天窗口而制造额外分支。

这套换窗检验**只增加一次短事实核对**，不得演变成重新研究所有资料、统一重跑所有旧验收或冗长交接仪式。不同工作线共享的是方法，不共享未经核对的 BEX 特定结论。

## 8. 在 BEX-01 M06 的首个应用

- 已核实 M06 曾发生行高 73px→58px 改善，但一批约 9 次提交中数次是测试定位/错误断言修复。下一轮不得简单沿袭“修一个行距→推送→全套 CI”的模式。
- 下一步：**直接读取 #909 原型 HTML/CSS/JS（精确来源见项目开发工作流 §5）**，提取功能/布局/颜色三维契约，并与 #1086 当前真实 Host 源码、真实交互和已验证能力一次性比对；集中修复共因，截图仅用于改后渲染/Human 验收；局部验证通过后对精确 HEAD 跑完整门禁。
- BEX 目标 **100% 高保真、真实可用** 不下降；M04–M06 仍按各自真实 Human/功能 gate 审核；不使用真实供应商文件、不进行未授权生产操作。
- 本规程本身**不宣告 BEX 完成**、不变更其里程碑或独立 PR 基线。

## 9. 简单验收：此规程是否真的提速？

下一轮交付按事实回答：

- 是否减少“无新证据的重复修复”？
- 是否先发现共同根因、且有至少一条明确的放弃当前路径信号？
- 是否减少仅为修测试选择器/断言而触发的远程重跑？
- 是否仍有精确最终 HEAD 的 required CI、真实功能与 Human gate 分层证据？
- 用户能否清楚看到**关闭了什么差距**而非只看到很多技术活动？

如流程本身开始引起大量表格/文档/额外检查，优先简化流程，而不是继续叠加仪式。

## 10. 复用证据与最小差异验证（2026-10-21 接续补充）

- 先核对最新 main、当前 owner PR/head 和失败记录；对**已完整读过且 blob 未变**的资料复用原阅读记录，只补读变更及关联章节。未读或只读片段不能靠 hash 升格为完整阅读。
- 把同根因的配置、作用域、缺失与恢复场景一次列齐，先做能区分方案的最小前后对照，再合批交付。原函数隔离探针只算局部证据，不能代替真实 Host/浏览器/数据库验收。
- 本地环境不完整时明确限制，先完成可可靠运行的定向检查，再集中提交到同一 PR；不为测试镜像重建产品逻辑，不承诺减少仓库自动触发的门禁。
- CI 失败同时记录源码 SHA 与实际工具链版本；已验证版本要可复现。固定版本不能冒充修复新版本兼容问题，升级须重过原门禁并保留未关闭责任。
- 收尾只写新增事实、失败/弃用路线、证据入口和下一条最小 gate；按实际关闭的用户差距评价效率，不以少写测试、PR 数量或长交接代替交付。
