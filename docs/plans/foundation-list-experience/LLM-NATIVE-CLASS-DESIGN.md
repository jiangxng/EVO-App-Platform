# EVO 的类架构设计

2026-11-06 · 架构设计评审稿。本文记录建议采用的语义与取舍。文中的类名、声明示例和评审步骤属于设计，不代表已发布的协议或已实现的功能。

## 1. 类解决什么问题

用户提出“增加业务字典”时，LLM 应能从已有类推导出需要支持的业务行为，并给出每项行为的来源。此次字典管理页定义了列表、逐项编辑、保存草稿和发布。它的验收范围也围绕这条路径，批量导入从设计到验收一路被漏掉了。仅增加“以后记得考虑导入”的提示，下一种插件仍然需要重新推断。参见[原字典页面评审](../../ui-design-reviews/enterprise-content-library-dictionary-20261104.md)。

建议将**类**定义为可复用、有版本的设计契约。类规定实例的业务职责、默认行为和必须保留的约束。开发者用 TypeScript、声明式清单或其他机制实现它，属于后续技术选择。同一个插件可以贡献多个不同类的实例，例如字典目录、字典项列表和编辑表单。插件继续承担安装、激活及业务所有权。

## 2. 把三个独立变化的维度分开

| 维度 | 类回答的问题 | 字典实例 | 总账分录实例 |
| --- | --- | --- | --- |
| 业务对象 | 一条记录如何被识别、修改、生效和引用 | 字典内的稳定选项编码，按字典版本发布 | 凭证内的行身份，已记账事实由记账流程产生 |
| 交互模式 | 用户怎样找到、比较、处理一组记录 | 可维护的选项列表 | 只读分录查询列表 |
| 能力接口 | 可以用什么输入、在什么条件下取得什么结果 | 批量准备字典草稿，导出选项，人工发布 | 按授权范围查询及导出 |

这样可以同时复用列表交互和保留领域差异。一份字典可以有列表、详情、编辑三种体验。一次导入也可以从列表入口或经授权的 Agent 发起，两者调用同一个业务契约。Eidos 负责通用交互，Platform 从有效贡献中组合入口并核对身份、企业与权限，业务插件决定数据含义和写入规则。

## 3. 继承、组合与覆盖的规则

1. **继承。** 每个维度只选一个主父类。例如“主数据维护列表”继承“业务列表”，增加主数据维护和批量准备草稿的设计义务。具体字典项列表继承后只填写差异。能按父类约定查询、分页和返回的调用方，也能使用其子类。
2. **组合。** 导入、导出、发布、审批等能力分别有自己的输入、结果、失败恢复和授权要求。类可以声明使用哪些能力。可选服务未安装时，类定义仍可被读取，宿主只在能力可用时加载实现。同一能力可被其他类复用。
3. **绑定。** 子类提供稳定的记录标识、字段、查询来源、导入目标、导出列或领域命令。标准行为直接继承。新字段或新动作写成局部扩展，保留稳定标识和来源。
4. **覆盖。** 可覆盖默认列、排序、布局和展示文案。影响业务的差异要给理由。多个贡献争用同一能力且语义不同，应显式选择或拆分，不按加载顺序取最后一个。子类不得放宽父类的企业隔离、字段权限或发布约束。如果一类记录从根本上不能接受某种写入，应选择合适的父类。
5. **版本。** 实例引用带版本的类。增加可选布局可作为兼容演进，改变稳定键、导入副作用或默认写权限需要新版本及迁移说明。保存的视图以字段 ID 关联，字段失效时提示修复。

每项能力另记两件事。**设计结论**取“继承、扩展、有理由不适用”，**实现状态**取“有证据可用、待交付”。两者分开记录。导入服务未启用属于运行条件，开发尚未接入属于交付缺口，已记账事实不能由列表写入属于领域约束。这三种情况会产生不同的设计结论。

**设计期与使用期各有一个问题。** 设计期先展开父类默认，再叠加实例差异，检查每个必需接口是否有业务归属。使用期才根据有效绑定、插件启用情况、当前企业、权限和记录状态计算此人可做什么。例如“导入到草稿”是字典项列表的设计义务，即使当前成员只能查看，设计清单中仍然有它。

## 4. 首个类族：业务列表

| 能力 | 业务列表的默认设计 | 具体实例需要提供的内容 |
| --- | --- | --- |
| 搜索、筛选、排序、分页 | 针对有权查询的整个结果集，稳定排序，显示范围，详情返回恢复原视图 | 可搜索字段、允许的筛选和排序、稳定键、查询来源。规模小时可在完整授权集合内本地处理 |
| 自定义展示列 | 选择、排序、恢复默认列 | 可读字段、必要身份列和默认列。隐藏显示列只改变呈现 |
| 保存与切换视图 | 将查询条件、排序、分组和列方案命名保存 | 个人偏好与企业共享视图各有作用域。切换企业、权限或字段版本时重新解析 |
| 布局及图标 | 同一视图可按任务选择表格、紧凑列表或卡片。命名视图可选 Eidos 标准图标 | 声明适用布局和图标。日历需要日期字段，看板需要适合分组的状态。单纯切换显示方式不修改记录 |
| 导出 | 列表须交代“选中记录”或“当前筛选结果”的输出语义 | 导出权限、可输出字段、格式与范围。翻页不截断“全部筛选结果”，导出时复核行列权限 |
| 导入 | 主数据维护列表默认有批量导入旅程。只读事实列表明确记录写入来源 | 业务目标、稳定键、新增/更新规则、校验、提交边界、回执和恢复；实际入口依赖插件启用、目标注册和当前权限 |
| 新建、编辑、批量操作 | 由业务对象类提供相应动作，列表就近呈现 | 合法状态、作用对象、数量、权限与后果。发布、过账、删除等动作逐项定义 |

查看状态不佳的记录应能用一个命名视图完成，例如“停用的字典项”，无需再给左侧导航增加同名入口。桌面用工具栏和列头承载高频动作，窄屏可折叠次要设置，保留文字标签、键盘路径和触控目标。打开详情、取消导入或处理失败后，恢复原视图、页位置及焦点。无记录、筛选无结果和读取失败应给出各自的下一步。

可复用的基础包括[现有 Eidos 表格契约](../../../vendor/eidos/src/catalog-browser/contracts.ts)、[往来对象投影查询](../../../apps/counterparty/projection-query.ts)和[导入目标契约](../../../contracts/foundation-object/import.ts)。已有计划把列表声明称为 `ListExperienceDefinition`，并区分企业共享视图与个人列偏好。这里继承这套分工；通用视图保存、自由选列和字典导入仍须分别接入和验证。参见[列表计划 §9](PLAN.md)及[投影架构 §12](../../architecture/FOUNDATION-OBJECT-PLATFORM-ARCHITECTURE-v0.1.md)。

## 5. 用三个实例推演设计

| 实例 | 继承或复用 | 实例自己的决定 |
| --- | --- | --- |
| 业务字典目录与字典项 | 同属业务列表。目录用于查找一套字典，选项列表用于维护字典项 | 目录的导入入口先选择目标字典，详情入口预选当前字典，二者进入同一流程。目录导出字典摘要和选项明细导出应标明范围 |
| 客户与供应商 | 同一往来对象的角色视图，共用查询、列配置和导入工作区 | 以主体稳定编码识别对象，保留客户及供应商角色。一主体兼有两个角色时，导入不会据此产生两个主体 |
| 已记账分录查询 | 继承筛选、排序、个人视图和受控导出 | 定义“列表直接导入分录”为不适用，理由是分录由业务单据过账产生。若将来有期初迁移，该操作需要自己的迁移及平衡校验契约 |

下面是研发时 LLM 应得到的**有效设计**示例。采用已有计划中的候选名称，写法用于说明分工，尚未指定清单格式或运行时 API。

```yaml
体验实例: 字典项列表
父类: 主数据维护列表 v1
业务对象: 受版本治理的字典项
记录身份: 企业 + 字典编码 + 选项编码
继承: [搜索, 筛选, 排序, 分页, 展示列, 保存视图, 布局与图标, 导入, 导出]
实例绑定:
  搜索字段: [选项编码, 名称, 来源别名]
  默认视图: 按选项编码排序，可按启用状态筛选
  导入目标: 当前字典的选项草稿
  导出范围: 选中项或当前筛选结果，明确草稿或已发布版本
  领域动作: 人工发布草稿
已知缺口: 批量导入和导出待交付
```

**纸面验收。** 实施人员导入“结算方式”时，先看到目标字典、待新增、待更新和冲突行。已有选项以稳定编码匹配，文件没有列出的选项保留；重复编码、与其他选项冲突的别名、版本已变化均须可定位并修正。第一次设计以一套字典为一个提交单位，全批校验通过后保存一份草稿，重试同一批有确定结果。已发布版本持续用于业务引用，直到有权人员另行发布。普通成员和未启用导入服务时也能查阅获准数据，直接调用写动作仍须经过同样的授权。

若一个设计只写“能搜索、能逐项编辑”，把它与父类展开结果相比较，就能直接指出缺少“导入目标、草稿边界和返回路径”。这就是该类对 LLM 的实际价值。当前字典页的目录搜索和逐项草稿已有实现，纸面旅程是待实现的设计。[字典页面](../../../apps/business-dictionary/page.ts)

## 6. LLM 如何使用类

每个类应有一张短的“类定义”，记录稳定名称与版本、适用任务和反例、父类、可组合能力、默认行为、领域约束、允许覆盖的位置及一个验收例。具体插件只保存自己的绑定和差异。建议按需读取该类及直接依赖，保留每个决定的来源，让使用不同模型的设计者能得到相同的默认清单。

每个能力用同一组问题描述：接受什么输入、读取或改变哪个对象、谁可以执行、成功返回什么、失败或重试会怎样。界面按钮、键盘操作和 Agent 工具是这项能力的不同入口。例如 Agent 可以准备导入草稿，人工发布仍是独立的领域动作。这种分离使插件更换界面或更换模型时，仍能沿用同一条业务规则。

在设计评审时，LLM 应交付三样东西：

1. **选类依据**：谁在做什么，记录如何进入、生效、被使用和退出。说明为何选“可维护主数据”或“只读事实”等业务语义。
2. **展开后的能力表**：列出每项的继承来源、实例绑定、适用条件和交付状态。遗漏、未绑定或无理由移除分别标记，不让沉默等同于决定。
3. **一条正常旅程和一个反例**：例如管理员导入一套字典草稿，与只读成员尝试同一操作。分别说明结果、失败后恢复，以及是否影响已发布数据。

先用字典、往来对象和已记账分录做纸面走查。如果两个同类插件需要重复设计相同操作，就把它提取为能力；如果为了复用必须绕开业务所有权，就重新划分类的边界。形成稳定设计以后，再决定清单语法、脚手架、自动检查以及 Eidos 实现方式。

## 7. 外部参考

SharePoint 把列、排序、筛选、分组组织为可命名的视图，并区分个人视图与公共视图。对 EVO 的启发是把“视图”独立建模，使它可以复用、保存和切换。[Microsoft Lists 视图设计](https://support.microsoft.com/en-us/sharepoint/lists/data-and-lists/create-change-or-delete-a-view-of-a-list-or-library)

Odoo 的列表支持选择记录后导出，也支持按稳定标识匹配导入数据。对 EVO 的启发是让通用入口携带具体对象、范围与身份规则；字典的草稿及发布仍由字典插件定义。[Odoo 导入与导出](https://www.odoo.com/documentation/master/applications/essentials/export_import_data.html)
