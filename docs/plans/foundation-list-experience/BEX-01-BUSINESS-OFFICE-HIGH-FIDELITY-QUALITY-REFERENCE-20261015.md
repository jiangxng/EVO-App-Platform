# BEX-01 → Eidos｜Business Office 高保真界面品质范例（2026-10-15）

> **性质：经真实用户正面反馈的参考范例与专项研究决策；不是新的 Eidos 设计权威，也不是已上线功能。** 未来正式跨业务采纳须由 Eidos owner 对照其既有 Human Experience / Productive / Business Office / Navigation / Mobile 规范评审。当前仅在 Platform 的 BEX-01 独立 Draft PR #909 中保存范例，不修改 Eidos 通用源码、公共 tokens 或全局项目状态。

## 1. 用户认可了什么，而不只是某个配色

2026-10-15，用户对 BEX-01 V2 高保真供应商导入工作页明确表示“可以用赏心悦目来形容”“后面的设计就要这种感觉”，并提出研究飞书背后的成套设计逻辑。此前的开发说明式原型受到否定：用户界面写满“模拟问题行、演示选择、非 Host”等词，导致业务使用者需要想象正式系统如何表现。新版用户肯定的是**视觉克制、信息秩序、中文业务语言、操作直接、细节协调**合在一起的总体产品体验；不能把这一反馈误译为复制 Feishu logo、字体、色值、组件外观或某一套静态 CSS。

**本次成功范例的定位**：

- 高保真源文件：\`docs/plans/foundation-list-experience/BEX-01-IMPORT-V2-HUMAN-REVIEW-PROTOTYPE-20261015.html\`；
- Chromium 实机验证及中文字体、手机字段控件修复：[run #38682435919](https://github.com/jiangxng/EVO-App-Platform/actions/runs/38682435919)；[桌面/移动/关键状态截图 artifact #11948338743](https://github.com/jiangxng/EVO-App-Platform/actions/runs/38682435919/artifacts/11948338743)；
- 测试结论：**14/14 Chromium 自动场景通过，且专项评审人员查看过桌面/手机截图**；不是用户本人完成 Human 正式签收；
- 画面所用 22 列/172 条供应商及三个异常记录属于**合成业务样本**，不是原 Excel/企业 Host 的真实数据。此来源声明进入 PR/文档/测试报告，避免在用户产品界面重复打断任务。

## 2. 解构“赏心悦目”：六项相互依赖的机制

| 维度 | 本页实际表现 | 解决的 Human 问题 | 反例与禁止 |
|---|---|---|---|
| 清楚的阅读路径 | 全局归属 → 面包屑和任务标题 → 进度与当前文件 → 数字摘要 → 需确认的例外 → 完整来源字段 → 唯一主操作 | 第一眼确认我在哪里、正在操作谁、要做什么 | 把技术配置、全部 22 列、危险操作一股脑铺在首屏 |
| 轻量的视觉层级 | 暖中性浅背景、白色业务表面、浅边框、低阴影、安静导航 | 可扫描、减疲劳，不因视觉噪音失去业务重点 | 大面积品牌渐变、高饱和装饰、所有卡片都突出、深色 IDE chrome |
| 成体系的间距/字体 | 标题-副标题成组、卡片内部紧凑、区块之间更宽；业务主信息略重，解释信息弱化 | 通过空间关系感知同组与分组，不反复靠边框 | 任意 13/17/29px 间距随手调整；所有字同粗同色 |
| 语义色有预算 | 品牌蓝主要留给动作/焦点，橙色留给待处理，绿色留给完成；中性色承担大部分版面 | 颜色成为可预测的业务信号 | 把警告/成功色当装饰，插件自造按钮蓝或多套调色板 |
| 异常优先，明细按需 | 高层先显示“3 项需处理”及就地动作，22 列仍能随时展开和修改 | 既让复杂业务完整，又不要求用户在几十项数据中寻找危险点 | 仅隐藏重要字段来做“极简”；又或者每项都展开成大表单 |
| 中文业务任务语义 | “3 条记录缺少主体类型”“选择字段”“预检查并继续”，其操作直接作用于当前记录 | 看得懂、点得动，不用理解开发者语言 | “DEMO-A / Schema / Host / 模拟问题行 / 业务字段 SDK”作为普通 UI 文案 |

**因果判断（项目团队分析，不是飞书官方原话）：**
舒适感 ≈ 看得出结构 + 少做无用判断 + 状态可预期 + 操作位置稳定 + 视觉噪音低。
上述机制共同成立才叫高品质。只换成浅灰背景和蓝按钮但仍然跨页丢状态，不算成功。

## 3. 飞书公开设计资料提供的印证（事实与 EVO 判断分开）

下列资料在 2026-10-15 检索。部分飞书开放平台页面在工具中只返回检索提取的正文，直接 HTML 打开时没有可用行内容；因此清楚标注证据等级，不冒充读取了不可见源码。

1. **飞书开放平台《响应式设计指南》**
   - 原网址：https://open.feishu.cn/document/design-specification/responsive-design/responsive-design-guidelines?lang=zh-CN
   - 等级：**检索工具返回章节与相关原文段落（正文可见）；直接打开网页返回零行**。
   - 来源事实：Web 端常用 8px 基础间距、小尺度 4px；移动端常用 4dp；以栅格/安全边距/断点和组件映射指导布局；移动端可把复杂表格/菜单/弹窗改为更适合窄屏的组件，不应仅机械缩小桌面内容。
   - EVO 采纳：保持与 Eidos tokens 对齐的 4/8 间距尺度与**语义保持、呈现转换**；表格在手机可变为卡片，字段和权限含义不变。

2. **飞书/Lark《Style / Visual specifications》**
   - 原网址：https://open.larksuite.com/document/tools-and-resources/design-specification/gadget-design-specification/visual-specifications/style
   - 等级：**检索工具返回相关正文段落；直接打开网页返回零行**。
   - 来源事实：中性色负责文本/背景/边框与层级，功能色负责编码状态；其指南提出页面文字颜色应保持少量、可识别。
   - EVO 采纳：低饱和中性色作为主要画布；蓝/橙/绿只承担明确语义。**不复制**飞书品牌色值与具体中性灰色阶。

3. **飞书应用引擎《常见页面设计原则》**
   - 原网址：https://ae.feishu.cn/hc/zh-CN/articles/768591170201
   - 等级：**检索工具返回可见正文摘要/相关段落；直接打开网页返回零行**。
   - 来源事实：先定布局骨架（上下/左右/T 形），再设计视觉元素和交互；提到固定内容宽度 1200px 等后台页面实践。
   - EVO 采纳：先定信息架构与页面分组，再审美化；内容宽度上限由 Eidos 与不同业务任务决定，**不是所有页面都硬编码 1200px**。

4. **飞书《多维表格应用模式》**
   - 原网址：https://www.feishu.cn/content/article/7578812241772924111
   - 等级：**已打开并阅读相关原文，包括“数据表/运行引擎”与“面向终端用户应用”分层**。
   - 来源事实：产品明确区分后台表结构与针对不同角色的应用化页面，减少终端使用者面对原始配置表的复杂度。
   - EVO 采纳：保持平台/字段/导入工具的完整性，但对一线用户呈现业务对象、当前决定和直达操作。**不**把飞书功能或权限实现当作 EVO 已具备。

5. **飞书/Lark《Message card design specifications》**
   - 原网址：https://open.feishu.cn/document/ukTMukTMukTM/ugDOwYjL4gDM24CO4AjN
   - 等级：**检索工具返回较完整可见正文**。
   - 来源事实：强调高效、灵活、直觉；“先主后次”、信息模块化、状态色有目的、常见操作就地可达。
   - EVO 采纳：这些原则可迁移到企业业务页面，但消息卡不是后台工作台，**不直接复制消息卡尺寸/布局**。

6. **飞书开放平台《抽屉》**
   - 原网址：https://open.feishu.cn/document/design-specification/component----feedback/drawer
   - 等级：**检索工具返回相关正文；直接打开网页返回零行**。
   - 来源事实：侧拉面板适合在不脱离主任务时操作附加信息，标题/内容/操作区可分别稳定组织。
   - EVO 采纳：字段说明、候选区别和局部更正优先上下文展开/侧拉，不任意跳页丢来源。

**结论（EVO 判断）**：飞书并不是靠某张“精致”图片维持一致性，而是靠组合的布局、状态、可访问性、组件和响应式规范；我们应该把“页面结果截图”转译为可复用**页面语法**，而不是另开颜色体系或复制飞书皮肤。

## 4. 在 Eidos 权威下形成可重复的页面语法

权威顺序维持：安全与无障碍 → Eidos Experience Architecture → Navigation/IA → Productive interaction → Business Office Visual Language → Mobile → Icon/token。**本规范是 BEX 的实例与检查表，不覆盖上述任何规则。**

### A. 先交业务骨架，再交视觉装饰

每个复杂业务任务默认设计以下可见骨架（可按任务取舍）：

\`\`\`
位置 / 面包屑
任务标题 + 一句话业务目的 + 适当的进度
当前业务对象 / 来源文件 / 业务身份
状态与问题数量（少量且能点击定位）
真正阻碍完成的例外 + 当场处理动作
完整信息（列表/表格/明细，渐进展开但不删除功能）
主操作 + 返回/恢复 + 保存状态
\`\`\`

不是每页强制 4 张统计卡；没有真实高价值数据时禁止造指标卡。列表页、表单页、详情页、Agent 工作台、2D Designer 各有不同的骨架，**先追求一致的行为和层级，再决定展示件数**。

### B. 控制视觉预算（值仅是现有成功原型量级，并非 Eidos 新 tokens）

- 中性色主导；品牌蓝只用于明确主操作、焦点、被选状态；警告、成功、错误语义色不滥用。
- 主标题约 24–28px；模块标题约 16–19px；正文约 14–16px；辅助说明 12–13px。实际字号以 Eidos tokens、文本缩放与可访问性为准，不能将 12px 当所有表单正文标准。
- 以 4/8 的节奏组织间距：控件内部 8–12，关联元素 12–16，模块之间 20–32。尽量遵守 token 刻度，不要为像素截图随意硬编码。
- 白色表面+浅边界+有限圆角（现有原型大多 8–12px）构建层级；不要叠加重阴影、粗描边、大色块与渐变。
- **主要动作每个当前任务作用域只有一个**；返回、取消、帮助、更多属于次要层。

### C. 美感必须服从工作流

- 用户常用动作直接操作，Agent 处理真正需推理/协作的部分；不得因“AI 原生”隐藏低歧义按钮。
- 先复用已确定映射、合法历史偏好和草稿，再请求用户纠正真实例外。
- 错误指出是哪一条业务数据、为什么失败、如何修复；就地恢复，避免跨页面回忆。
- 新建 Schema、预检查和正式数据提交有不同业务副作用；视觉上可以构成连续流程，但授权不能合并。
- 数据的“忽略”属于一个可撤销的决定，而不是丢失来源列/原始值。

### D. 桌面与手机保持同一语义，但允许不同形态

- 桌面：适当密度的表格、横向关联、展开行，支持扫描和批量操作。
- 手机：一条业务记录/来源列一张核对卡，上方是名字和状态，下方是样本和可完整看到的操作控件；避免让用户横向寻找隐藏下拉。
- 同样保留来源值、身份、角色授权和错误；不是简单删除字段的“移动精简版”。
- CI 的浏览器字体必须包含真实中文字符渲染能力；无 CJK 字形的截图不具备中文产品设计验收资格。

### E. 高保真原型的真实性与诚信并存

- **用户可见画面**必须像产品：真实业务语言、数据预览、完整选项与可信状态，不重复写“演示选择”“模拟问题行”“非 Host”等研发解释。
- **评审外层**必须如实标明合成数据、未连接真实 Host、用户数据尚未验证、未签收，不能用“导入完成”的演示画面宣称正式写入。
- 所有状态按钮都必须可交互并可测试，至少包括加载/空/阻断/完成/返回修改/刷新恢复；仅漂亮静态截图不算完成。

## 5. 跨业务推广：应复用原则，不复用一张固定模板

| EVO 场景 | 同一设计理念的具体落地 |
|---|---|
| 供应商、往来对象、存货/仓库 | 业务对象名称明确；概览先于长字段表；例外就地修正；详情与来源可追溯 |
| Ledger Manager / 定义与版本 / Projection | 先说明当前定义和状态；主要操作靠近账本版本；技术编译/协议进高级详情；投影视图保持业务名称 |
| 2D Designer | 画布是视觉主角，控制栏安静；少量显式当前工具和状态；快捷操作就地可达；不强加四卡片仪表盘 |
| Personal Agent / Workbench | 对话与待执行业务动作是主角；工具与诊断弱化；Agent 协作不替代低成本直接操作 |
| 数据列表/导入历史 | 表格密度适合工作；表头/状态/过滤/批量操作一致；移动使用可读卡片；错误与可恢复入口可见 |

跨业务**必须再次遵守** Eidos 现有导航归属、权限边界与组件 owner，不允许 BEX 的静态 HTML 被复制粘贴到共享运行环境。

## 6. 以后怎么验收“这种感觉”：四层证据

1. **视觉品质**：桌面与手机真实中文截图可读；标题/内容/状态/主动作有清楚主次；不要争抢注意力。人工能在几秒内指出下一步。
2. **交互品质**：业务任务能连续完成、例外可定位、选择可恢复、失败可修复、字段不丢失，不强迫重复决策。
3. **实现一致性**：Eidos tokens / 组件 / 导航与状态语义一致；移动不是桌面的机械缩放；权限与安全不降级。
4. **证据诚信**：源码静态核验、自动 Chromium/CI、截图人工复核、真实 Host/Excel/User Human 签收分开标注，任何一项不能冒充另一项。

### 设计 review 六问（可给下一窗口直接使用）

- 用户只看前 5 秒，能否知道在哪里、处理什么、下一步是什么？
- 哪三个视觉元素是全屏最重要的？有没有多余元素抢注意力？
- 是否尽可能保留既有选择，而不是把复杂度推给人？
- 是否每个异常都能就地处理、失败后可恢复？
- 在 390px 手机与中文 200% 放大时，关键控制是否真实可见可操作？
- 能否让业务用户把该页面当成产品而非技术说明书，同时在文档里如实交代未接入真实业务？

## 7. 与原有 Eidos 设计规范的关系及后续 owner

此文档仅补充**经过用户认可的 BEX 页面作为完整实例**与对照证据，**不建立第二套 design tokens、视觉系统、全局规范或无需评审的“自动美学评分”**。建议由 Eidos owner 在既有 \`EIDOS-BUSINESS-OFFICE-VISUAL-LANGUAGE-v0.2.md\` 和 \`EIDOS-HUMAN-UI-DESIGN-REVIEW-CHECKLIST-v1.0.md\` 下，将“真实中国业务文案、内容秩序、中文字体截图、桌面表格→移动可操作卡片、业务错误恢复、四层证据”转化为可复用范例和审查条件；由 Platform 本窗口维护 BEX 原型和用户决定记录。

**验证边界**：此文件的存在与 Chrome 14/14 仅表示该合成案例经原型级核验；不代表真实 22 列 Excel、原 Import Job、正式 Host/Owner、Railway 或 Eidos 通用组件已经完成用户验收。
