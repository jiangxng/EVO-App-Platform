## 真实用户发现的问题

用户已在 Railway 页面实测：“默认支付方式”单字段流程会预填业务字段名称并在返回后自动选中（可用）；但紧接着“结算方式”“默认账期方式”“账期天数”仍分别需要打开创建页、保存和返回。**逐字段闭环可用 ≠ Excel 导入整体可用**；这是重复点击成本问题，不应继续修补成更复杂的逐列向导。

用户先前明确：一个 Excel 列 ↔ 一个系统目标字段；已选目标要从其他下拉消失并在释放后恢复；忽略是有意识选择；新增字段只作为本企业的扩展，基础对象核心/主体类型规则不能被覆盖。

## 定向阅读与采用依据（2026-10-15）

1. **Airtable 官方《CSV import extension》**，已读相关原文（字段映射、表头识别、跳过字段、自动匹配、样例预览、复用映射、导入前确认）：
   https://support.airtable.com/articles/3067164948-csv-import-extension
   来源事实：先把 CSV 列按名称尝试与已有表字段匹配；剩余列可人工选择；保留跳过选项，映射可复用；导入前可看样本记录。**采用**：已有字段优先、用户集中复核、少重复导入；**不采用**：直接以 Excel 新建任意 EVO 物理对象。
2. **Microsoft 官方《Create a list based on a spreadsheet》**，已读相关原文（从 Excel 表头生成列表列、创建前字段类型选择）：
   https://support.microsoft.com/en-us/sharepoint/lists/data-and-lists/create-a-list-based-on-a-spreadsheet
   来源事实：Excel 的表头和内容可用于一次生成列表结构。**采用**：整表字段集中处理；**不采用**：把一个供应商导入文件变成新的无约束业务对象/自由建表。
3. **ClickUp 用户关于导入重复生成字段的反馈**，已读原讨论：https://www.reddit.com/r/clickup/comments/1jjqm3n 。
   单一社区案例，并非总体统计；印证“优先复用现有字段，不能每次建重复”。

## 最少步骤的产品行为（推荐实施）

- **A. 自动识别与分流，不创建任何字段**。载入原导入作业时：①已确认映射/有效 recipe 优先；②目标字段唯一且语义确认可对应的，自动建议复用；③没有对应字段且属于可理解的企业业务属性的列，默认列为“准备新建”；④系统 ID、日志、时间戳等元数据、敏感或歧义字段列为“需要确认”而非静默建字段；⑤“忽略此列”作为用户主动选择。
- **B. 在映射页提供显眼的“集中处理 N 个未匹配字段”动作**，一屏展示来源列、系统建议（匹配现有/准备新建/忽略/需确认）、拟创建的业务名称（默认 Excel 表头）、推荐类型（文本保守默认；数字/日期必须根据有效样本和业务语义判断），可逐项调整；高价值差错例如“账期天数”和金融编码字段要能改类型。不要再逐个跳单字段页。保留单字段操作供例外情况使用。
- **C. 用户一次确认“创建并加入映射”**。只对选定的新建企业字段保存定义，重用已有定义而非再次创建，随后把每条来源列对应到其目标字段，并返回原映射页直接显示选中状态。用户无需再次点击保存或寻找新字段；“已创建字段”和“已导入供应商数据”必须明确区分。最终的导入预检查和提交仍显式分离。
- **D. 必须可恢复与防重复**。一次确认前完整检查权限、字段名称/类型/占用关系以及同名冲突；服务端防止重复系统目标映射或重复字段创建，不能仅隐藏控件。若保存过程部分失败，重进页面要显示哪些字段已创建并可复用，继续剩余项，不产生二次重复。对过去已存在的两条“开户银行”绝不自动合并/删除，需查看引用关系后人工确认。
- **E. Agent 非必经环节**。保留原 `ai-auto-map` 动作及上下文；未来 Agent 可只生成映射/字段建议草案，不能绕过 Owner/权限、批量创建确认、核心 `subjectType` 校验或导入显式提交。三行缺失的“主体类型”仍须核实实际来源，不能自动以“往来类型”代替。
