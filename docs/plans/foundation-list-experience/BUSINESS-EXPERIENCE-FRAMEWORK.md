# 企业业务应用通用体验框架：桌面、平板与手机

日期：2026-10-12（香港）  
状态：**PROPOSED / 实施设计提案**；本轮仅补充计划，不表示列举的业务插件、流程引擎或控件已经实现。  
关系：本文件是通用上层框架；[原计划](PLAN.md)是其中基础对象/列表/导入的第一条实现切片。

## 1. 用户需求的专业表述与覆盖边界

建议正式名称：**企业业务应用通用体验框架**（Enterprise Business Application Experience Framework）。

可以这样描述需求：

> 建立基于元数据与插件贡献、支持桌面/平板/手机自适应的企业业务应用体验框架。以统一设计系统、页面模式库、状态驱动动作和可恢复任务旅程，覆盖主数据、业务单据、执行作业、申请审批与分析应用。各插件声明领域语义、权限和能力；共用框架实现一致的导航、布局、列表/明细、表单、审核、反馈、AI快捷辅助及可控页面扩展。

相关术语的区别：

| 术语 | 回答的问题 | 例子 |
|---|---|---|
| Design System / 设计系统 | 视觉和基础交互如何一致 | 字体、颜色、间距、按钮、输入框、图标、无障碍 |
| Information Architecture / 信息架构 | 功能从哪里进入 | 应用、我的待办、业务管理、设置、上下文链接 |
| Page Patterns / Floorplans / 页面模式 | 一类工作怎样组织页面 | 列表详情、表头明细、工作队列、审核页、向导 |
| Experience Architecture / 体验架构 | 用户能否完成任务 | 目标、对象、状态、动作、完成、异常、恢复 |
| Adaptive Experience / 多端自适应体验 | 同一任务在不同设备怎样完成 | 桌面明细表格变手机逐行编辑，业务规则相同 |
| Contribution / Extension Slots / 页面贡献与插槽 | 高级插件怎样加入 | BI链接、详情页签、只读洞察部件 |

原文档不能称为“已经满足所有业务应用”。它覆盖列表/对象/导入基础，本补充增加业务单据、履约执行、申请审批与完整移动任务设计。目标是让这些应用有可复用的体验骨架，不是宣称一套模板能处理所有未来领域，也不是新建通用ERP业务引擎。

## 2. 与 Eidos 现有体系的关系

沿用 Eidos 已有 Experience Architecture、导航架构、Productive Design Language、Business Office Visual Language、Mobile Design Language 和 Icon System，不另造平行设计语言。

平台固定的体验契约已包含 collection、detail、overview、work-queue、editor、review、setup、explorer、conversation，以及 journey/actions/agent/quality。这说明已有可继承的架构基础；**不说明这些页面的所有业务控件已经齐备**。

分层职责：

1. **Eidos设计系统**：视觉token、控件、键盘/读屏、手势替代、通用反馈。
2. **Eidos页面模式与多端实现**：布局、页头、集合工具栏、表单、明细、审核、页面部件容器。
3. **宿主组合与导航**：授权、插件激活、有效页面/动作/贡献发现、可信上下文、路由与任务返回。
4. **业务插件**：对象/单据/申请语义，状态迁移，字段规则，关联引用，数量/金额/日历规则，执行与回执。
5. **AI辅助**：准备和解释已声明的任务，始终使用相同的业务能力与权限边界。

Eidos可以渲染“批准”动作，不能自行决定谁能批准；可以展示“可出库量”，不能计算库存权威或绕开并发校验。框架复用的是交互规则，不是强制所有业务共享状态机。

## 3. 页面模式库：组合使用，不按插件复制页面

| 模式 | 适用目标 | 共用区域 | 领域可声明内容 | Eidos架构映射 |
|---|---|---|---|---|
| 集合工作页 | 查找、筛选和处理记录 | 视图、查询、选择、动作、数据区 | 列、筛选项、行/批量动作 | collection |
| 对象详情 | 理解一个基础对象 | 身份摘要、业务面、相关记录、历史 | 角色/属性/扩展面 | detail |
| 单据工作页 | 创建和处理有明细的业务单据 | 表头、明细、汇总、状态、关联单据 | 行字段、计算结果、转换动作 | detail / editor |
| 申请编辑页 | 填写并提交报销/请假等 | 申请信息、条件字段、附件、校验、提交 | 申请类型、规则、额度/余额 | editor |
| 工作队列 | 集中处理待办 | 我的待办、分配、到期、优先级、预览 | 工作项来源、领取/处理动作 | work-queue |
| 审核决策页 | 理解变更并作决定 | 摘要、明细/差异、依据、意见、决定 | 审批规则、允许的决定 | review |
| 执行作业页 | 完成仓储等现场操作 | 对象识别、待处理量、本次量、异常、确认 | 批次/序列号、位置、任务约束 | bounded-task editor |
| 分步向导 | 高风险或多阶段输入 | 步骤、当前结果、前后导航、恢复 | 步骤数据及确定性校验 | setup / editor |
| 分析探索页 | 观察与钻取 | 指标、筛选、图表/表格、口径 | 指标定义、来源、分析链接 | overview / explorer |
| 会话辅助区 | 处理歧义和解释 | 上下文、任务进度、建议/差异、返回 | 已声明任务类型与能力 | conversation |

模式可以嵌套但应限制深度：单据页中嵌明细表，行复杂信息打开侧区或独立页；手机不连续叠加多个抽屉。一个页面明确一个主要目标，不能同时变成报表、审批、数据维护和聊天工作台。

## 4. 用户举例的应用如何套用

以下是体验设计映射，**不是这些业务插件已完成或本轮要全部开发的承诺**。

| 应用 | 主要页面组合 | 关键差异，必须由插件负责 | 手机优先任务 | AI捷径候选 |
|---|---|---|---|---|
| 基础对象 | 集合＋对象详情＋编辑＋导入 | 身份唯一性、关系角色、归档和引用约束 | 搜索、查看、补资料 | 字段识别、错误解释 |
| 销售 | 订单集合＋单据工作页＋关联履约 | 客户、价格/币种、税额、数量、部分履约 | 查单、补备注、提交/审批 | 从询价材料准备订单草稿 |
| 采购 | 订单集合＋单据工作页＋收货关联 | 供应商、采购单位、交期、授权、分批收货 | 查订单、审核、查看到货 | 供应商报价列匹配/比较建议 |
| 出库 | 待执行队列＋执行作业＋结果回执 | 库位、可用量、批次/序列号、部分完成 | 扫码/选品、录数量、确认异常 | 解释异常、整理操作说明 |
| 调拨 | 调拨单＋发出作业＋接收作业 | 来源/目标位置、在途、部分接收和差异 | 发出、接收、核对差异 | 解释差异及准备处理建议 |
| 费用报销 | 申请＋费用明细＋附件＋审核 | 发票/币种、重复报销、政策、预算、支付状态 | 拍票、填明细、提交/审批 | 票据字段提取、政策检查提示 |
| 请假 | 申请＋额度说明＋审核＋历史 | 日期/时段、工作日历、时区、假别、余额、冲突 | 快速申请、撤回、审批 | 自然语言填写申请草稿 |

销售、采购是业务单据，不只是“基础对象多加几列”；调拨通常有发出和接收两种工作，不是一个状态下拉框；报销审批完成不等于付款完成；请假时长由工作日历/规则确定，不由LLM自行算。

## 5. 单据与申请页面的固定结构

### 5.1 页头与摘要

名称/单号、当前主状态、关键对象、主要日期、责任人、当前允许的主要动作。技术ID和协议信息折叠。业务流程较复杂时，用易理解的状态摘要解释“当前到了哪里、下一步由谁处理”。

列表、详情和手机上使用相同业务名称，不把桌面的“提交申请”在手机改成语义不明的“完成”。

### 5.2 表头—明细—汇总

- 表头承载共同信息：交易对象、单据日期、币种、业务组织等，只出现适用字段。
- 明细承载重复行：物料/费用项、数量、单位、单价等；稳定lineId独立于显示行号。
- 汇总来自领域服务，说明是否含税、币种和舍入规则。客户端可预览，但提交后以服务器校验结果为准。
- 添加行提供“选对象”“从来源单据引用”“复制行”等已声明操作；来源行保留可追溯引用，不能只有显示文字。
- 批量粘贴/导入先进入预览与校验；无权字段、错误单位、无效引用不能偷偷接受。
- 行错误定位到具体行/字段；允许保存未完成草稿时，应明确草稿不等于业务提交成功。
- 保存草稿、提交、批准、执行、过账是不同动作；使用不同授权/确认和回执。

不强制所有业务使用表头明细：简单请假采用单表单即可，不能为统一视觉制造无意义的“请假明细表”。

### 5.3 关联、附件与历史

正文后提供来源/后续单据、适用的附件、评论与业务时间线。评论不等于审批意见；业务时间线不暴露完整内部日志。

附件显示上传、识别、失败、可重试状态；拍照/选文件只是入口，文件类型/大小/安全检查及访问权限由服务约束。OCR/模型结果是可修改的候选，保留原附件引用，不把识别文本当原始证据。

从关联单据返回时恢复原单据页签与位置。批准后需跳转后续执行时，提供显式下一步，不让用户只能回列表猜入口。

## 6. 状态驱动动作与完整任务旅程

框架支持表达任务状态，不定义统一业务状态枚举。各插件声明可用动作，宿主检查当前身份与权限，领域服务再校验当前状态和并发条件。

| 状态维度 | 示例 | 共用显示原则 |
|---|---|---|
| 文档状态 | 草稿、已提交、作废 | 显示是否可编辑 |
| 审批状态 | 待审批、退回、批准 | 显示当前处理人与可执行决定 |
| 执行状态 | 待出库、部分发出、部分接收、完成 | 显示已完成量/剩余量和异常 |
| 结算状态 | 未付款、部分支付、已支付 | 与批准/履约分开，来源明确 |
| 同步/任务状态 | 上传中、处理中、结果未知 | 不覆盖业务状态，说明可否重试 |

不把上述所有状态挤成一枚“状态”标签。列表展示最相关主状态，详情展示必要的次级维度。

每个动作的候选描述至少包括：稳定operationId、作用范围（对象/明细/多选）、标签、可用条件、权限、输入Schema、影响预览、确认要求、幂等/并发要求、成功回执、下一步和失败恢复。它是对现有能力契约的设计要求，最终应复用/扩展已有契约，而非另建与之冲突的执行通道。

每条任务必须定义：入口→先决条件→输入→校验→确认/执行→可证实结果→后续去向→异常恢复。只有按钮和表单不算完整体验。

审批任务需证明处理者有权、任务仍有效；通过前展示关键内容和必要差异。转交、加签、撤回、委托、批量审批只有业务插件明确支持时才展示。审批与执行可分开，各自重新检查权限；通用UI不自动批准。

部分失败必须逐项返回成功/失败/未处理；重试范围明确。不可逆业务不得提供虚假的“撤销”，应调用 owner 支持的冲销/撤回/修正流程。

## 7. 全平台交互与设计语言要求

| 通用方面 | 必须统一 | 插件可以不同 |
|---|---|---|
| 视觉 | Eidos颜色、字号、留白、边框、密度、图标 | 业务名称、领域标识、合法状态含义 |
| 动作 | 一个作用域通常一个主要动作；危险操作分离；更多菜单规则 | 哪个操作是当前主要动作 |
| 输入 | 必填、单位、帮助、错误定位、只读呈现 | 业务规则和字段适用条件 |
| 反馈 | 保存中、成功、失败、处理中、结果未知分明 | 回执内容与下一步 |
| 导航 | 面包屑、返回、深链、恢复状态 | 业务路由与关联关系 |
| AI | 明确上下文、建议/应用/提交分开、可取消与返回 | 可辅助的任务种类 |
| 无障碍 | 焦点、读屏、对比、文字缩放、非手势替代 | 领域的可理解标签与解释 |

不把设计语言等同于皮肤，也不把“所有页面看起来一样”作为验收。列表、审批、仓储现场操作应该有共同规则，但信息密度和主要动作不同。

通知只用于轻量结果；需要用户修正的错误留在工作页面。重要结果提供回执和可再次查询入口，不依赖两秒后消失的toast。等待较久的任务必须能离开后恢复。

## 8. 手机端是一等体验，不是桌面缩小版

### 8.1 继承现有 Eidos 规则

已核对平台 `vendor/eidos/src/design-language/mobile.ts`：统一断点由Eidos控制，当前手机阈值700px；单列主工作区、安全区、无全页横向滚动；导航使用底部主要目的地；交互目标至少44px；遵循系统文字缩放；插件不得私设移动端壳和断点。

这些是当前Eidos政策的引用，不是本文件新建的像素规范。后续token调整从owner统一采用；不得把700px和44px复制到每个插件私有CSS。

### 8.2 页面转换矩阵

| 桌面模式 | 手机实现 | 必须保留的语义 |
|---|---|---|
| 密集列表表格 | 紧凑记录列表，关键字段在首层，其余展开/详情 | 全部有权字段可到达，不静默丢字段 |
| 主从双栏 | 列表→详情逐页前进，返回恢复 | 同一选择、查询、滚动位置 |
| 多列表头表单 | 单列分组，条件字段渐进展开 | 规则、错误和必填一致 |
| 明细网格 | 明细行卡片；点击进入单行编辑；前后行切换 | 行号/lineId、数量/金额、错误与汇总 |
| 固定右侧详情/AI区 | 全屏页或受控sheet，一次一个任务面 | 草稿、上下文、返回状态 |
| 审核对照表 | 摘要→关键变更→必要明细→决定 | 不能隐藏影响决定的关键数据 |
| 多图表分析 | 摘要指标→单图→钻取；复杂配置可转桌面继续 | 范围/单位/权限/来源口径一致 |
| 扫码录入 | 相机/扫码适配与手工输入并存 | 身份识别后仍需业务验证 |

宽表有确切比较任务时可在**表格容器内**有意横向滚动，不能导致整个页面横向滚动。可选择的数据呈现不同，但数据和操作语义相同。

### 8.3 手机动作与输入

- 页面级关键动作放在统一可达操作区；底部导航与表单提交条不能互相遮挡。进入专注编辑时按Eidos壳规则收纳导航，不能每插件自己决定覆盖层。
- 键盘弹起时输入框、当前错误和提交路径仍可见；安全区和系统手势区预留。不能只测试桌面模拟宽度。
- 金额/数量使用合适输入提示，日期/时段明确时区；格式化不改变实际精度或吞掉编码前导零。
- 点击替代悬停；滑动、长按、扫码都要有可见按钮/手工替代。危险操作不设为单次滑动直接生效。
- 保存草稿与提交明确分开；是否允许自动保存由任务声明，自动保存只保存草稿，绝不能自动批准/出库。
- 拍照/OCR请求相机权限前解释目的；拒绝权限后仍可选文件/手工录入，不能卡死流程。
- 草稿从服务器恢复需要相同身份和企业权限；本地缓存含敏感数据时必须有明确政策，默认不把业务附件和整表持久存在浏览器。

### 8.4 弱网、重连和设备续接

手机优先保证可恢复，不默认承诺完整离线业务。首期离线时保留允许的未提交输入并明确“未提交”，不在后台静默排队执行批准、出库、调拨或支付。

网络超时分为“确定未提交”和“结果未知”；后者先凭operation/request标识查询回执，再决定是否重试。按钮防连点不能替代服务器幂等。

跨设备继续使用服务端草稿/任务引用，重新授权并做版本冲突检查。若草稿能力未实现，则明确提示需要保存，不宣称设备间自动同步。

复杂建模/透视配置可以标明适合桌面处理，手机仍能查看、处理其所承诺的核心任务和恢复；不以“手机空间小”为由隐藏审批所需证据。

## 9. LLM 捷径在各类业务中的一致原则

采用“任务旁的明确辅助入口”：导入页自动匹配、单据页从资料准备草稿、报销页识别票据、请假页用自然语言填写、审核页解释异常。

所有AI结果都经过同一链路：当前授权上下文→建议或草稿→结构/业务校验→差异展示→用户应用→业务提交。读取说明可以直接返回；涉及金额、对象关系、日期、审批和执行的建议必须按领域规则确认。

例：“下周一下午请半天假”可以建议假别/日期/时段；用户看到解析后的绝对日期和时区，业务服务根据人员日历/余额计算实际扣减。例：“根据这张发票报销”生成候选金额/币种/日期和原图对应，不直接认定合规、不直接付款。

模型不负责合计金额、库存可用量、请假余额、业务状态迁移。截图、附件与表格中的内容是待识别数据，不能指挥Agent越过宿主权限。

手机AI面板必须能回到原任务；应用结果不覆盖用户并发修改；AI不可用时核心申请/单据仍可人工完成。不把频繁确定性操作强制变成聊天。

## 10. BI 与业务插件扩展到所有页面模式

保留原计划的 LINK 与页内部件两条路径，并推广到单据、申请和工作队列。

| 页面 | 链接扩展 | 页内贡献候选 | 禁止行为 |
|---|---|---|---|
| 集合 | 当前筛选分析 | 查询摘要、质量提示 | 绕过行级权限计算统计 |
| 对象详情 | 对象业务分析 | 洞察卡、关联业务页签 | 写入主数据派生金额 |
| 单据 | 关联交易、履约分析 | 历史、成本提示、风险说明 | 替换领域汇总/批准/执行权威 |
| 申请/审核 | 政策、相关申请 | 重复风险、证据摘要 | 将AI风险判断当自动拒绝/批准 |
| 工作队列 | 团队工作负载 | 合法范围的统计 | 泄漏其他人的敏感任务 |

候选宿主插槽继续采用少量稳定位置：relatedLinks、summary、insights、tabs、assist，按页面类型命名；不随每个新插件新增一个硬编码位置。部件贡献声明支持的surface、最低可用宽度/密度、可降级呈现与语义摘要。

同一部件在手机优先变成可打开的摘要或独立页；不能把桌面iframe按比例缩小。当部件不支持手机时明确可用替代入口，而不是显示空白。

卸载、超时、撤权、版本不兼容时只隔离扩展区域；基础单据与申请仍可按已有能力完成。第三方嵌入经过专门集成适配器及安全治理，不能获得任意页面代码注入权限。

## 12. 实施范围修订与验证矩阵

原计划L0–L5保留，但L0必须检查本框架，避免只为Counterparty定制。首批仍只落实基础对象列表/导入，不立刻新开发销售、采购或HR业务。

复用验收分三层：

1. **控件/模式层**：Eidos用明确标记的合成夹具覆盖列表、明细、申请、审核、执行和移动布局；夹具通过不等于业务插件完成。
2. **实际集成层**：先基础对象，再选择一个已有真实owner接口的表头明细业务；申请/审批模式只有接入真实领域规则后才可标为可用。
3. **产品层**：各插件逐项验收其声明的任务。未开发的功能标未实现，不用通用框架演示掩盖。

| 代表任务 | 桌面必验 | 手机必验 | 关键失败场景 |
|---|---|---|---|
| 基础对象导入 | 匹配/校验/结果/返回 | 查看结果、纠正字段、返回 | Recipe失效、只读字段、AI超时 |
| 表头明细单据 | 多行编辑/校验/提交 | 新增/修改一行、看汇总、提交 | 并发修改、精度/单位错误 |
| 出库/调拨执行 | 部分执行与回执 | 手工/扫码识别、确认数量 | 重复提交、数量变化、接收差异 |
| 费用申请 | 附件/费用行/提交 | 拍照或文件上传、复核后提交 | 上传失败、重复票据、识别错误 |
| 请假申请 | 时段/日历规则/提交 | 申请、绝对日期复核、撤回 | 时区、跨天、余额变化 |
| 审批 | 看依据、决定、下一步 | 无需横向找按钮即可完整决策 | 任务过期、无权、结果未知 |
| BI部件 | 查询一致、钻取、返回 | 摘要→详情、返回 | 超时/未授权/停用不影响主任务 |

移动验收至少包含窄屏与横屏、iOS Safari和Android Chrome的实际任务、软键盘、大文字、弱网和屏幕阅读/键盘路径。具体设备版本由实施批次记录，不能仅凭CSS断点截图宣称移动验收完成。

发布门禁：每个插件提供页面/任务/设备覆盖表，逐项标“已实现且已验收 / 已实现待验收 / 不适用及理由 / 未实现”。只有被证明的范围能称为覆盖；不能用“通用框架”四字承诺无限适用。

## 13. 专项增补结论与下一步

本次补充后的文档体系，规划范围已经覆盖用户列举的七类应用及手机端，但仍是**通用体验设计与实施要求**，不是“所有功能已经具备”。后续增加新领域时优先组合模式，只有发现新的任务形态才扩展框架。

下一步L0输出一个简短缺口清单：现有Eidos模式/控件、待补通用能力、对象插件应声明的信息、手机首批任务。L1仍做供应商列表与导入；之后用一类真实单据检验表头明细复用。审批/库存/财务/HR规则继续归各业务owner，不借体验框架扩大平台Core。

专业描述以后可直接用：**“请按企业业务应用通用体验框架建设这个插件，包含对应页面模式、状态驱动动作、任务恢复和手机端适配，并预留受控插件扩展与AI辅助入口。”**
