## 一、视觉科学与设计原则：研究结论

1. **视觉复杂度先于信息理解形成第一印象。** Tuch et al. (2012) 两组实验研究网页截图视觉复杂度（VC）与典型性（PT）对早期审美印象的影响。较低 VC、较高 PT 的网页在实验中获得较高美感评价；这**不是**“17 毫秒内完成 UX 理解”或“低密度等于高任务成功率”。EVO 应减少重复边框、满屏链接、连续相似表单控件，保留已有软件的熟悉定位方式。
2. **视觉层级必须符合任务优先级。** 视觉传达从尺寸、对比/饱和、粗细、放置位置和留白形成。NN/g 建议界面避免大量相互竞争的重点；EVO 首先看见“文件已分析/是否安全”，第二看见“何处需要我的决定”，最后看到“继续预检查”。UUID 不应比业务结果更醒目。
3. **格式塔接近、相似与共同区域原则。** 人倾向把邻近、样式相似或同一边界内的元素当成同组。正确做法是利用一致行排列与组间空白合并语义，而不是给每一列一个卡片/单独边框；大区块边界不要多到制造“假页面结束（false floor）”。
4. **浏览与扫视不是机械 F 形。** NN/g 原眼动研究存在 F、跳点、分层/阅读等多种模式，受任务、网页结构影响；不要把 F 型当成屏幕排版公式。对本页更适合清晰的分组标题、左侧业务字段名、相邻建议状态、极少可操作的异常列表。
5. **节奏来自稳定网格、排版和留白，而不是控件越小越好。** IBM Carbon 的 2x Grid 与间距系统强调布局几何、跨页面对齐、一致的信息密度模式，且明确指出重复无变化与缺少留白会造成单调。EVO 可采用与 eidos 兼容的 4/8px 节奏作为**候选**，优先复用 eidos tokens，不直接复制 Carbon CSS。
6. **美观不能掩盖功能缺陷。** NN/g 的 aesthetic–usability effect 说明美观可能让人宽容轻微问题；用户测试仍必须量化真实字段正确率、可逆性、AI/权限、最终导入正确性。不要把漂亮截图当签收。
7. **可访问性是一条独立的视觉最低标准。** WCAG 2.2 AA：普通文本至少 4.5:1（大字号满足条件时 3:1），识别控件与重要 UI 状态的非文字视觉信息至少 3:1；颜色不能作为状态唯一标识。需验证键盘焦点、放大 200%/400%/窄屏重排而非只做正常桌面截图。

## 二、原页面视觉缺陷的具体诊断

| 原界面特征 | 视觉认知负担 | 视觉整改 |
|---|---|---|
| 长面包屑与字段映射重复标题在上方争抢视线 | 页首没有唯一焦点，重要文件内容被挤到下面 | 以 `导入供应商` 为主标题；文件名放一行次级；返回入口合并成轻量导航；不突出内部路径 |
| `Import Job` 与 UUID 成为主表单字段 | 强行让用户先识别技术编号，干扰任务目标 | 移到 `导入详情/技术信息` 的折叠区；普通用户默认只见文件名与当前步骤 |
| 22 项宽大下拉+22 条创建链接 | 每条都有高对比蓝色文字，视觉重点失效，滚动无尽 | 默认只给组别摘要和真实例外；所有列在“查看全部字段”之后用紧凑可编辑行展示 |
| 同样的“建议创建”对“系统编码”和真实业务列一视同仁 | 视觉相似性暗示业务含义相同，易诱发误创建 | 四类语义状态，待判定的系统列只能“保留来源/需复核”，不能直接视作新建业务字段 |
| 多段提示像系统设计说明书 | 阅读成本大，用户反复看到与自己无关的机制 | 简短自然语言“已安全保留原始列；只需检查问题项”，规则解释移到可展开帮助 |
| 各行都占屏幕大面积 | 高密度业务审阅被长表单取代，缺乏对齐对比 | 默认摘要+例外清单，详情 48–56px 行高候选（以 eidos token 为准） |
| 只有浅色蓝链接作为主要视觉信号 | 轻重不分、无清楚反馈 | 主 CTA 唯一高对比实心按钮；次要为文本操作；仅错误/警告用语义颜色+图标+文字 |

## 三、视觉设计方案：界面结构优先于控件样式

### 3.1 第一屏的视觉阅读顺序

```text
返回供应商                              第 2 步 / 共 3 步   [次级、低权重]

导入供应商                              <- 第一视觉焦点
往来账户2026_10_08_10_15_23.xlsx        <- 文件上下文
已安全保留原始文件内容                    <- 可靠性反馈

[ 已识别 · 实际数量 ] [ 建议新增 · 数量 ] [ 仅保留来源 · 数量 ]
（数字由当前 Import Job 实际分析，禁止伪造或硬编码“22 应新建”）

需要你确认                               <- 第二视觉焦点；仅实际有例外时显示
  主体类型      有 3 行缺少真实数据        [查看问题行]
  开户银行      存在两条同名候选          [选择目标]
  （其他真实歧义，不按数量强行凑三个）

  查看全部 22 列及映射建议 ›               <- 次级入口

[ 返回 ]                          [ 确认字段并预检查 ]  <- 唯一主 CTA
```

*以上 3 行缺失、两个同名“开户银行”来自已知前序交接，只有当前真实作业存在且判断达到门槛时才显示；类别计数一律运行时生成。切勿伪造本 Excel 的“已识别几列”数据。*

- 若当前没有待确认项：不显示空异常卡片，改用克制的确认文案；仍保留查看完整映射。
- 若数量很大：只显示最值得处理的前若干项 + “查看其余 N 项”，不出现 22 个等高卡片。
- 若 AI 未完成/不可用：状态文字标记“已用历史规则完成、其余待检查”，不能虚报“AI 已完成”。
- 真正必须 Human 解决的主体类型/重复目标阻塞要用说明文字告诉用户为什么；允许修改而非只显示禁用按钮。

### 3.2 视觉权重约定（适配 eidos，而非重新定义 eidos）

| 层级 | 视觉方案（拟定值需按 eidos tokens 验证） | 禁止事项 |
|---|---|---|
| L1 页面主题 | 22–26px / 600–700，整页通常只有一个主标题 | 大字号 UUID、同一行多个同等级标题 |
| L2 章节分组 | 16–18px / 600，关键区域标题 | 每行都使用章节级粗体 |
| L3 字段/正文 | 14–16px / 400–500，尤其中文正文优先可读；行高约 1.45–1.6 | 通过 11–12px 字号塞进更多字段 |
| 补充说明 | 13–14px / 400，低视觉权重但仍符合文本对比要求 | 大段灰色极浅文字；把唯一业务解释放 tooltip |
| 横向阅读 | 内容区域建议约 960–1120px（需实际屏幕测试），左对齐，明细表格可自适应扩展 | 中央悬浮的窄长 22 级巨大单列下拉 |
| 间距 | 基准以 eidos token；候选基本单位 8px；组件内部 8–12px、相邻行 12–16px、板块间 24–32px | 每行多重边框、多重阴影、不规则跳距 |
| 颜色 | 灰阶/界面中性色为主体，品牌主色只给予主操作；警告/错误按语义分配 | 为每一个统计卡片配不同饱和色造成视觉噪声 |
| 图标 | 与文字一起说明状态，图标形状统一、大小 16–20px | 仅凭红/绿、纯图标或多个“+”表示决策 |
| 边框/卡片 | 大分组必要时轻分割；优先用空白分组 | 为 22 项分别画卡片和大面积背景填充 |
| 操作 | 每个阶段 1 个主操作；次级为轻量文字链接或菜单 | 主按钮、创建、AI、忽略对等出现在每一行 |

这些数字只是为设计实现提出的**候选默认值**，不是科学研究得出的唯一正确像素，更不能绕过 eidos 已有字体/间距/按钮约束。

### 3.3 四类状态的视觉映射

1. **已识别（低注意力）：** 用中性文本与小对勾；合并统计数字，默认折叠。匹配来源可展开为“以前用过的设置/按名称确认/AI 建议”，不要把 RECIPE、EC、DETERMINISTIC 字样当标题。
2. **建议新增（中等注意力）：** 提醒有多少企业字段待一次确认；列表中用文案“建议新增 · 文本/数字”，不为每项渲染整宽蓝色链接；用户可一次选择并审阅完整拟新增清单。
3. **保留来源（低注意力）：** 显示“原表已保留，暂不写入业务字段”，可随时调整；不能当作丢弃。
4. **需要决定（高注意力）：** 只有真正阻塞者使用醒目的图标、明确的字段名称和可执行的微操作。警告与错误不只靠颜色；若更改产生外部作用需二次确认。

原始 Excel 列都保持在导入作业中；正式的扩展字段创建以及最终的供应商入库，仍分别由 Human 明确确认。**视觉方案不能暗中改变已批准的业务安全边界。**

### 3.4 “查看全部字段”的完整信息密度策略

这里用 `table` 或 eidos 已有列表组件，而不是 GOV.UK 的 summary list：GOV.UK 官方明确建议 summary list 适合 key/value 回顾，不适合表格式数据；USWDS 则提供表格密集信息、斑马纹和移动堆叠方案。

桌面明细行结构（建议）：
`Excel 原列（左对齐，可按需展示样本） | 系统建议目标 | 映射依据（轻量） | 状态 | [修改]`；
- 行高 48–56px 候选，在触屏/放大时自然增长，不裁剪中文。
- 同类已识别行可折叠；需要确认的行置顶；可筛选“全部/待确认/建议新增/已识别/保留来源”，但**不要默认使所有筛选工具常驻**。
- 轻网格线或行距择一；只对有可读性收益的表格考虑隔行背景，避免同时厚边框/斑马纹/整列高亮。
- 首列必须始终能定位原 Excel 来源名称；查看来源样本时需授权与必要脱敏，不能因视觉方便泄露个人资料。
- 修改建议用单列的行内编辑或已有 side panel；不允许重新跳转 22 个完整“创建字段”页面；修正后回到列表原位置。

移动端/窄屏：
- 概览纵向排列，异常行按“字段名、问题、修复操作”自然换行，不把桌面 5 列生硬压窄。
- 详情按单项可展开的行/抽屉呈现，操作可达、焦点回到原项；长文案不会压住主按钮。
- 扩大文字与 400% 缩放下仍能完成核心任务；不让横向滚动遮住字段名称或确认状态。

### 3.5 视觉模式的验收，而非主观“好看”

A. **3 秒视觉层级测试**（研究启发但阈值为产品验收候选，非文献定量结论）：给真实业务用户看首屏 3 秒，随后问“这是干什么的、已经完成什么、下一步是什么”；统计回答正确率。
B. **模糊/眯眼测试**：把首屏略微虚化，正确显现主标题 + 异常区域 + 主 CTA，蓝色链接海和 22 下拉不应该成为焦点。
C. **双任务可操作性**：至少跑“第一次导入无映射”和“第二次有历史映射”；记录完成时间、首次正确理解率、实际修正次数、误创建正式企业字段数、错误恢复率。
D. **强制异常路径**：用真实三行 `subjectType` 缺失、两个同名“开户银行”、系统编码/流程状态等列；异常能被发现且不默认污染 schema。
E. **对比度与无障碍**：测文本 4.5:1、非文字关键状态 3:1、键盘焦点和文字缩放；色盲模拟中可依靠图标+文案区别状态。
F. **跨设备**：桌面 >= 1280 宽/窄桌面约 768/手机约 390；需要时增加非整数缩放/200%/400% 放大核验。上述宽度是测试场景而非浏览器断点的硬编码要求。
G. **功能边界**：原 Agent 上下文不丢、已有字段一对一排他仍成立、未批准不写正式 schema、预检查/最终导入各一步、失败恢复能回到对应字段。

### 3.6 研究中的冲突、适用条件

- **“少即是多” vs 复杂领域必须审查**：不能把 22 个字段直接消失；选择“首页摘要 + 用户可进入完整明细”，既减少默认视觉负担又维持审计能力。
- **彩色帮助识别 vs 颜色过载/无障碍**：颜色只是增强视觉语义，统一以文字/图标表达。不要用 4 个同样饱和的颜色作为四组计数卡片。
- **白空间 vs 企业高密度表格**：默认概览应有空白，专业用户展开表格后密度可以提高；不要用“宽松”迫使专业用户多滚十屏。
- **摘要式回顾 vs 表格式对照**：概览可使用轻摘要，22 行映射必须用对齐可比较的结构；不要把 GOV.UK summary list 错用成复杂数据表。
- **学术第一印象 vs 真实任务成功**：Tuch 摘要只支持审美评价变化，不支持“越简越好”对所有场景无条件成立；需通过本项目实际任务验收。
- **eidos 设计语言 vs Carbon/USWDS 数值**：吸收共性而非整套拷贝；CSS、icon 与现有 eidos 控件原型保持一致，缺少通用控件时另提 eidos 负责方。
- **截图和数据分离**：用户页面显示 22 未匹配的原因不是视觉研究能确认的，`import-33ff3446-80c5-4992-b5c6-710f415535b3` 具体来源字段与映射记录仍需经授权核验。
