## 发现：空白启动不等于最小宿主

`manager/server.ts` 的安装/迁移逻辑会在空白状态自动装入16个包。除身份、授权、上下文相关能力外，包含往来对象、导入、扩展字段、2D/3D运行图、企业观测与瓶颈分析。报告保存完整列表。

部分逻辑检查“Feature未激活”就调用install（如3D Viewer、企业观测），另一些检查“包未安装”。因此必须逐项核对重启是否恢复用户已停用/卸载的能力；本轮是代码发现，尚未执行所有插件的重启矩阵，不能宣称全部插件都有该问题。

## 已确定的治理方向

1. 首次初始化：通过明确的安装配置选择默认包；最小配置保留必要认证/授权，业务插件由用户选择。
2. 升级迁移：版本化、一次执行、记录完成结果。兼容迁移不应成为每次重启重新安装业务包的长期机制。
3. 日常启动：恢复已持久化的安装与启停选择；除安全基础要求外，不因某业务插件缺席而自动补装。
4. 对已部署实例保留兼容默认，不直接改变现有安装。先以独立测试覆盖空白启动、升级、停用重启、卸载重启，再引入显式最小模式。
5. 同时对账资源owner：Provider Registry的remove当前只清理Map，不负责dispose；宿主生命周期有processHost.stop和BI关闭钩子，但没有覆盖所有进程内Provider。必须分清“删除登记”与“释放资源”。

## 试点选择与限制

非关键瓶颈分析Provider是按需加载候选：确定性只读计算，无远程写入；当前宿主静态导入并直接创建。但它本身没有连接/定时任务，**不能单独作为资源释放成功的证据**。

下一步先完成启动策略对账，再选择具备实际资源生命周期且可隔离运行的试点。BI已有close可作为参考，但其数据库资源试验需隔离数据库；不为演示释放而制造无意义常驻资源。正式账本、凭据和生产登录不作为首个改动试点。

本轮CI新增自动采样与报告附件，远端运行使用Node 22.22.2；各环境分别留基线，不能混算为性能回归。
