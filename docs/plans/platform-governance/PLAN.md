# EVO 插件平台整体治理规划与分步执行

> 2026-10-14范围修订：用户要求以插件合理性与架构缺陷审查为主，不继续扩展运行试点。当前任务及完成标准见[审查接续入口](REVIEW-ENTRY-20261014.md)。下文保留为长期背景，不代表所有GOV阶段均需在本次额度内实施。

日期：2026-10-13（UTC）  
状态：方向依据用户确认目标；具体接口及迁移细节为待逐批验证的实施方案。规划完成不等于运行能力完成。

## 1. 整体目标

平台不是一次性启动完整ERP、再隐藏菜单。宿主提供最少的安装、生命周期、授权、路由与能力组合；业务、模型、检索等按需装载。没有页面的能力也可成为插件，但不是每个内部函数都应拆成独立包。

LLM原生意味着业务语义、可调用能力、任务进度与上下文明确且可治理；确定性校验、计算、权限与事务仍由软件负责。模型可替换，企业规则、记忆和任务不应随模型更换而丢失。

成功标准：用户不需要理解几十个技术插件才能工作；管理员能看懂依赖、影响和健康状态；开发者能按同一机制增加新插件；少装插件确实减少无用装载、任务和资源。

## 2. 现有架构权威与职责

继承现有[扩展边界宪章](../../architecture/EXTENSION-BOUNDARY-CONSTITUTION-v0.1.md)、[项目边界](../../architecture/EVO-ECOSYSTEM-PROJECT-BOUNDARIES-v0.1.md)、[宿主基础](../../architecture/PLUGIN-HOST-FOUNDATIONS-v0.1.md)、[Agent状态与上下文宪章](../../architecture/AI-NATIVE-AGENT-STATE-CONTEXT-CONSTITUTION-v1.0.md)及[企业—个人学习闭环](../../architecture/ENTERPRISE-PERSONAL-LEARNING-LOOP-LONG-TERM-v0.1.md)；本计划不以重写这些文档代替实施。

| 层 | owner | 职责 |
|---|---|---|
| 宿主 | EVO-App-Platform | 清单发现、依赖解析、生命周期、可信上下文、授权边界、路由/组合 |
| 通用体验 | Eidos | 控件、页面模式、手机实现、无障碍、通用交互 |
| 领域应用 | 各业务插件 | 业务对象、规则、状态迁移、操作与回执 |
| 替代服务 | Provider插件 | 模型、身份、凭据、检索、外部资源等实现 |
| 确定性业务执行 | EVO/相应领域owner | 记账、库存/财务事实及确定性执行 |
| 企业知识学习 | Experience-Compiler | 跨角色经验、证据、假设、学习与改进建议 |
| 个人任务体验 | Personal Agent | 个人工作上下文、任务组织、授权能力使用 |

治理专项只约束接口、生命周期与整合方式，不把上述业务语义移入平台Core。

## 3. 插件划分与保留规则

判断独立插件的依据：独立替换价值、配置/凭据边界、权限边界、可选依赖、独立生命周期或部署需求。没有页面不是反对理由；有一个manifest也不是充分理由。

| 类型 | 处理原则 |
|---|---|
| 独立业务应用 | 保持独立安装及领域owner |
| 多供应商服务 | 相同契约、不同实现；显式选择绑定，不按名字判重复 |
| 同一产品的前后台 | 可分包；用户入口聚合，依赖透明 |
| 固定内部实现 | 优先模块/同包Feature，不强迫用户单独安装 |
| 历史兼容别名 | 验证真实引用再退役，不误算成两个插件 |
| 实验与未完成业务 | 本轮不处理展示和业务补完，保持原专项状态 |

每个待调整包记录：职责、调用者、数据owner、配置、绑定、启动条件、资源、停止方法、兼容别名、迁移与回滚。先证明依赖关系，再决定合并/保留，禁止凭卡片标题删包。

## 4. 真正按需运行的生命周期

| 状态 | 目标行为 |
|---|---|
| 未安装 | 只读轻量清单；不加载重型实现、默认业务数据或启动服务 |
| 已安装未启用 | 可查看配置；不后台运行；存储保留 |
| 已启用待激活 | 可发现能力；重型资源延迟至声明事件/首次调用 |
| 活跃 | 创建受管实例、连接、订阅和后台任务 |
| 停用中 | 阻止新调用；按策略等待/取消已有任务；记录中断与回执 |
| 已停用 | 关闭连接、任务和订阅；清除可丢弃缓存；不删除业务数据 |
| 卸载 | 移除安装/代码资源；共享依赖按引用关系处理；数据删除另行治理 |

工程重点：manifest与实现分离；禁止以导入清单触发业务服务初始化；用统一factory/activation/disposal边界承接资源；首次并发调用只初始化一次，失败可重试；停用与激活竞态有明确状态。

Node进程内模块通常不能可靠卸载其模块缓存。延迟import能减少未用代码装载，dispose能释放业务资源，但不能保证停用后RSS恢复启动值。必须强释放的插件采用已有可用的受管进程隔离边界或经验证的新适配；不要把进程内停用宣传成彻底卸载内存，也不为每个小插件强开进程。

独立安装包和按需下载属于进一步的分发目标，第一阶段不为追求包体立即重建商店、签名或分发系统。发布体积、启动装载、活跃资源三个指标分别记录。

关键身份/权限/凭据服务需有宿主保护：关闭后拒绝新受保护操作，不提供隐式绕过；有依赖时拒绝直接卸载或要求明确处理依赖。不能为让“停用成功”而关闭安全检查。

卸载不等于删数据。业务数据由既有企业资源/领域存储管理；可重装恢复。清除数据是有预览、备份和明确授权的独立动作，不由本计划自动执行。

## 5. 账本管理与发布转换器

用户产品入口统一为账本管理：草稿、待发布、正式版本、版本选择与发布结果。定义持久化仍沿用企业定义权威，不在编译器再建立另一套版本库。

编译器负责合法性校验、表达式解析和向运行时配置的确定性转换；不制定业务规则、不实际记账、不拥有发布审批。对用户呈现为发布流程中的“校验/准备发布”阶段，后台实现可替换。

目标链路：选定定义版本→校验与编译→运行时接收/确认→记录可核对发布回执。编译成功不等于已发布生效；网络结果未知时按发布请求标识查询，不盲目重发。来源版本、编译器版本、产物摘要、目标运行时及回执需能关联。

当前存在账本管理直接调用编译器源码，以及旧bookkeeping格式约束。先固定最小编译接口和现有输入输出回归样本，再整合为受管内部依赖；是否保留独立可安装packageId由调用者/部署证据决定。旧packageId、配置、能力引用迁移前保持兼容，不能先删清单。

禁止把规则编译器与Experience Compiler合并：前者是确定性发布转换，后者是企业知识与学习。

## 6. 登录与个人/企业上下文

登录会话回答“请求是谁”，Agent上下文回答“本次任务需要知道什么”，二者不能混称会话。

正式用户默认托管登录会话；静态会话归开发测试；预配置Bearer会话只保留明确的受控集成/兼容用途。先核对绑定与调用者，再逐批限制适用环境，不断开现有认证。托管会话自身可处理Bearer，因此界面不要把Bearer传输形式当成另一种用户身份。

| 状态/数据 | owner与用途 |
|---|---|
| 个人上下文/记忆 | 个体偏好、方法、允许保存的经验；个人范围 |
| 对话与当前任务 | 原始对话证据、工作状态、执行进度分层保存；可恢复 |
| 企业资源与规则 | 企业共享对象、正式定义；确定性业务事实留在所属运行时 |
| 企业知识与经验 | EC从经治理证据形成组织级学习；保留来源、冲突与有效范围 |

企业整体视角取自授权的跨部门业务事实、事件和经过治理的工作成果，不依赖全员聊天汇总。拥有组织级分析任务不等于所有员工能读取全企业数据。敏感字段、个人隐私、跨企业边界仍受保护。

模型请求按任务编排个人偏好、当前工作、企业证据与可用能力；先查询/计算/检索，再装配最小充分上下文。不把整个企业或历史对话全部塞入模型。

个人经验进入企业知识需明确来源、适用范围、脱敏和治理；企业经验供个人任务引用，不默认复制到所有个人记忆。模型建议不能直接改变正式规则，必须走领域发布/执行流程。完整学习闭环继续按现有长期目标分步实施，不因本规划立即启动新知识平台。

## 7. 后台服务与用户入口

用户理解的入口：账号与登录、企业空间、个人Agent、企业知识与改进。技术依赖可在管理员视图查看其用途、消费者、配置、健康、替代实现和停用影响。

这是目标信息架构，不把尚未完成的企业知识功能伪装成已可用页面。后台分组不要求把所有服务代码合成一个大插件。保留共享契约，按生命周期价值决定包粒度。

交易示例和未完成插件展示明确排除本轮范围。BEX页面框架由原窗口推进，治理专项只提供所需的能力与生命周期约束，不重开BEX任务。

## 8. 分步路线

| 编号 | 范围 | 交付与完成标准 | 前置 |
|---|---|---|---|
| GOV-00 | 现状对账 | 固定提交、包/调用/资源证据及未知项；静态与实测分开 | 本轮首批 |
| GOV-01 | 资源基准 | 最小宿主、代表性组合的启动/内存/后台任务/连接测量；明确环境与配置 | GOV-00 |
| GOV-02 | 生命周期试点 | 一个非关键Provider证明延迟激活、并发保护、停用释放、重新启用与失败恢复 | GOV-01 |
| GOV-03 | 账本发布依赖 | 明确编译接口与owner、兼容旧输入、发布回执；用户入口统一 | GOV-00及账本owner对账 |
| GOV-04 | 身份服务收敛 | 正式/测试/兼容用途明确，绑定迁移和认证回归 | GOV-02机制稳定；身份owner协作 |
| GOV-05 | 上下文契约对齐 | 个人/任务/企业事实/EC边界和证据授权明确，复用Agent已有实现 | 原Agent/EC owner共同对账 |
| GOV-06 | 后台产品组织 | 依赖自动解释、管理员分组、停用影响展示 | 生命周期与职责证据可用 |
| GOV-07 | 扩展与回归 | 经验证机制推广至其他包；新增包接入检查 | 试点指标达成 |

顺序以GOV-01→02为第一实现链，不同时启动全部阶段。每批小提交、可回滚、一条实际任务可用后收敛。其他owner变更只有该阶段真正涉及才创建对应PR；不提前为每个待办建分支。

## 9. 性能与可用性验收

同一Node版本、机器、数据库、数据量和配置，对比最小安全宿主、一个业务插件、常用组合。分别记录冷/热启动、可用时间、空闲/活跃RSS及heap、CPU、连接、定时任务、插件实例、首次调用延迟、停止后的资源计数。

最小安全宿主保留正常认证授权，不用关闭安全服务来制造漂亮指标。指标观察不发真实业务写入或模型请求；外部资源用明确隔离环境。

至少测三轮相同条件，记录范围与波动。先建基线再定预算；不能编造“降低50%”或把未激活菜单隐藏当性能优化。验收未安装插件无业务任务/连接、同一插件不会重复初始化、停止不再产生新工作、卸载不误删数据；内存指标考虑GC和模块缓存限制。

可用性以功能结果为准，不要求用户为每项提供截图签收。自动化测试、可重现步骤、结果回执和用户实际使用反馈是证据；截图只在定位视觉问题时使用，不作为甩包袱门槛。

### CI架构约束（用户确认，2026-10-13）

“轻量宿主、业务能力按需装载”必须通过自动化检查持续约束。首批执行[CI门禁](CI-GATES.md)：宿主入口的静态业务依赖不得扩张、遗留清单只能缩减，未激活动作不得加载实现，首次并发加载共享实例且失败可重试。所有PR及main推送运行，不以路径过滤漏掉间接依赖。

后续GOV-01/02必须补充运行层门禁：未安装/停用插件无连接与后台任务，停用后停止新工作，重新激活可恢复；资源指标先建立可重复基准再制定预算。静态门禁通过不等于这些运行层目标完成。

## 10. 迁移、回滚与协作

每次调整前记录旧绑定、依赖、配置和数据位置；不在报告中暴露密钥。以兼容适配替代一次性改名；有持久化变化时先证明迁移和回滚，避免双写成为两套权威。

停止/卸载与进行中任务冲突时先明确drain/cancel策略；无法安全中断的操作返回阻塞原因。已完成业务用回执确认，不因客户端取消否认已执行结果。

本专项改动限治理计划、必要最小生命周期机制及具体试点；不接管业务主线、BEX、Agent、2D和EVO独立开发。待办追加自己的GOV区，不修改其他窗口状态。全局status与生成handoff的陈旧项移交主线协调，不在本轮整体覆盖。

每阶段记录：负责人/窗口、固定基线、实际变更、验证、未决项、PR、下一步。代码合并不等于线上生效，文档合并不等于功能完成。涉及部署、破坏性数据清理另按当时授权执行。
