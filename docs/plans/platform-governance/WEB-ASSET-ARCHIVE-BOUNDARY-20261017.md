## 目标与已有事实

用户要求轻量宿主、业务按需装载，并把原则落实到后续准入。导入目标全量解析已在#1004–1006闭环；本批只核对既有宿主资源归档债务，不扩大到CDN/PWA/插件商店。

完整读取 `manager/web-asset-archive.ts`、原归档测试、`manager/web-delivery-cache.ts`及`docs/architecture/WEB-DELIVERY-AND-SURFACE-ADOPTION-v0.1.md`（分段补读截断部分）。定向读取server归档构造、监听前ensureCurrent、旧/当前资源GET与诊断入口，app-host-shell入口、浏览器主入口及可达模块的动态import/iframe线索。复用已完整读过的装载架构第11节。未访问生产文件、客户浏览器或外部网页；未声称通读整个server。

代码事实：

- archiveRoot来自显式配置，或lifecycleStateFile同目录的web-assets；无archiveRoot则不归档。
- sourceRoot是dist根；监听前调用ensureCurrent，遍历复制所有.js，追加生成的shell CSS与.ready。不是import/执行这些JS，也不是浏览器下载证据。
- 同revision有.ready时直接返回，因此不是每次重启都重复全量复制。
- 新revision完成后按.ready时间清理旧快照，默认保留5、期望限制2–20；旧页面可能在升级后才请求懒加载依赖，保留范围不能按当前已安装插件裁剪。
- 当前revision从实时dist读取，旧revision从归档读取；相对ESM import继承revision前缀。只改“第一次请求时保存该文件”会漏掉升级后才首次打开的旧版功能。
- 当前archive.revisions()列出目录而非仅ready快照，readArchived不检查.ready；不把现状描述成原子发布协议。改归档算法时必须明确失败/重试与不完整快照可见性。

## 方案比较与决定

| 方案 | 决定及理由 | 条件/限制 |
|---|---|---|
| 按当前安装/启用包裁剪 | 排除 | 旧页面后续功能、共享依赖和重新启用无法由当前安装状态决定 |
| 每个文件首次请求才归档 | 排除作为默认方案 | 未访问但稍后需要的旧版本依赖会丢失；需完整不可变部署产物可重新获取才可成立 |
| 后台异步全量复制 | 不作为首选 | 减少监听前等待但不减少复制量；升级/停机中断产生不完整快照，需要发布协议 |
| 简单复制固定几个目录 | 排除 | 业务浏览器模块可能跨目录；目录名不是稳定所有权/依赖合同 |
| 构建期生成浏览器资源清单，再按清单保存版本快照 | 选定下一步方向 | 先确认全部入口、延迟依赖与其他资源；构建严格校验，生产不用开发解析器；旧版本兼容必须实测 |
| 删除归档，要求所有用户刷新 | 排除 | 破坏已打开页面及当前版本兼容承诺 |

以上取舍是针对本项目代码和已确认目标的工程判断，不冒充外部行业研究结论。轻量宿主并不意味着所有静态文件必须按安装包数变化；部署级共享浏览器产物可以合法存在，但不应把全部后端实现当作浏览器资源。

## 下一批明确范围与验收

先实现一个有界“构建清单＋受控归档”改动，不同时重写资源路由/浏览器框架：

1. 复核唯一shell入口、移动/桌面动态入口、独立iframe和资源URL；需要额外根时显式声明。构建清单包含相对路径与内容hash，覆盖生成shell CSS的归属；未知引用/漏文件拒绝生成，不默默缺失。
2. 生产归档只消费已验证清单；缺失/损坏清单如何失败或兼容旧部署必须明确。已存在的旧完整归档继续读取，不删除或就地重写旧revision。
3. 发布.ready前验证所有指定资源；失败不标完成，重试结果可解释。并发首次创建、同revision一致性和保留策略用实际文件测试证明，不能仅断言文件数减少。
4. 真实Host双revision验证：旧页面在新Host上首次请求旧延迟依赖仍返回原字节；当前/旧JS与CSS的ETag、304、immutable语义保留；不存在的旧资源仍404，不能回退成新版文件。
5. 沿用真实Chromium桌面/手机/供应商流程CI；按四组合审计记录文件/字节变化。只有这些通过才关闭资源归档整改，不把本次94文件观察冒充完成。

浏览器资源路由目前允许的路径较宽、历史归档不完整可见性、revision/retention输入校验均是接入时必须复核的兼容/边界条件。本批未把这些独立扩成安全专项，也未宣称已修复。
