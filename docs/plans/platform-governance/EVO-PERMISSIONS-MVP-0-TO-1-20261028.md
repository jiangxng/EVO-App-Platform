# EVO 权限中心 0→1：优先解决创建企业权限与可理解的错误

**日期：2026-10-28；状态：用户已确认优先级，实施规格候选；不是已上线功能。**
本方案补充本目录现有 IAM 与 SaaS 套餐规划，不再建立第二套权限服务。

## 一、范围收敛与未来弹性

用户明确：EVO 未来可能走众包、独立复制部署、多租户和多种获利模式；这些目前不定型。现在应当做出**最小真正可用的权限管理页面**，首先解决创建企业时报 STATIC_POLICY_NO_MATCH 的问题，避免每次临时修改服务器权限规则。

固定下来的仅是通用权限接口：当前部署实例、真实用户 Principal、动作 Action、资源 Resource、作用范围 Scope、允许/拒绝和审计记录。

- 平台管理权属于**当前独立部署实例**；将来复制部署时，另一台实例可以有独立 Platform Owner、用户和策略，不要求共享中央身份或商业中心。
- 企业所有权属于具体 Enterprise Context；用户 A 有创建企业资格，不等于 A 是平台管理员；A 创建企业后才成为那个新企业 OWNER，不自动成为其他企业 OWNER。
- 未来众包的发布任务、接任务、审核、结算等权限都可以通过新的 Action/Resource/Scope 声明扩展，不把权限引擎硬编码成只有企业员工。
- 套餐和收费以后单独通过 Entitlement/Usage 决定，不将付费直接映射为权限，不提前开发支付模块。
- 继续轻量 Host、业务插件按需安装，Eidos 负责界面；权限事实和判定属于 Host/Provider，不由 UI 过滤或普通业务插件代替。

## 二、第一版页面只有两个视图

### 平台管理 → 权限管理（必须是可信平台管理员）

- 用户清单：来自已经认证、可撤销的真实身份目录；状态为有效、停用。
- 基础权限：第一版仅展示和管理“创建企业”资格。可以给指定用户授予/撤销，显示授权者、日期、状态与审计。不开放任意通配符权限或操作原始策略 JSON。
- 用户搜索和权限原因查询：看得到谁能创建企业，以及为什么不能。管理按钮操作前检查、二次确认，服务端每次重验。
- 后续才加应用管理权限、企业创建限额、有效期、审批、众包相关权限等。

### 我的权限（所有已登录用户）

- 看到当前真正身份、是否有创建企业资格。
- 无资格时显示“尚未获得创建企业权限，请联系平台管理员”，而不是提交后看到 STATIC_POLICY_NO_MATCH；有资格才可进入创建流程。
- 企业创建提交时服务器仍重新校验。成功后自动成为该企业 OWNER、自动选择企业，并在刷新后保持；不自动安装业务插件。
- 用户被撤销创建资格后，不能再创建新企业，但已经创建的企业 OWNER 不会被自动删除。

## 三、必须先解决的安全前置条件

东京验证环境现阶段共享 demo-user 与 Basic Auth。它适合单人验证，但**不能直接作为正式平台超级管理员，也不能凭这个共享身份授予其他人的真实平台权限**。首版授权写页面上线前，必须先引入/验证真实用户登录与可信的平台管理员初始化。

建议交付顺序：
1. M0：只读“我的权限”与创建企业前置检查、清楚的中文错误提示；保留现有拒绝规则。
2. M1：真实用户身份与首次平台管理员安全初始化；明确只有部署所有者可以首次设定，不可让首个访客自封超管；禁用/撤销生效。
3. M2：有权平台管理员可以在页面为用户 A 授予/撤销创建企业资格，持久化且立即生效，有审计。
4. M3：实际验证 A 创建企业后 OWNER 与 Grant 同步生成；取消资格、跨企业和越权负向测试均通过。

**不是**先做套餐、角色矩阵、众包结算、支付或每种数据字段权限。M0 不能包装为 M2 页面已完成。

## 四、后端与 UI 边界

- 重用既有 Authorization Provider、Host User Directory、Enterprise Context Governance Store；不新增一套与之并行的权限引擎。
- 授权配置不能永远只靠修改环境变量再重启：页面 M2 必须写入持久的 Grant Authority，并确保多 Worker 并发更新、审计和吊销一致性。不可把管理权限写入用户可编辑的插件设置。
- 服务器始终做最终权限检查，显式 DENY 优先。UI 先查询“可执行/为何不可执行”，并只呈现非敏感拒绝原因。401、403、缺企业、缺业务服务和无权限都应有不同的中文提示。
- 平台管理入口不应与“企业管理”及普通“设置”混用；企业成员授权以后由企业治理 Experience 展示，但数据和判定仍在 Host/Provider。
- 独立实例权限只在该实例有效。后续若商业模式选择集中多租户，可增加可选中央授权 Provider；不能现在假设每套部署必然共享用户或账单。

## 五、0→1 验收标准

| 场景 | 必须满足 |
| --- | --- |
| 未授予权限的用户 A 打开创建企业页 | 看见明确原因，不暴露内部错误，服务器拒绝创建 |
| 平台管理员为 A 授予资格 | 仅目标 A 获权，立即生效，有操作审计 |
| A 创建企业甲 | 成功，A 成为甲 OWNER，刷新后仍存在 |
| A 创建企业乙 | 依当前资格政策受控允许，甲/乙成员与数据互相隔离 |
| 管理员撤销 A 创建资格 | A 无法再新建企业，原已创建企业与 OWNER 关系保持 |
| B 访问 A 企业或调用授权写 API | 服务器必须拒绝；UI 不作为授权证据 |
| 独立复制 EVO 到另一实例 | 没有未经授权同步 A 的用户、授权或企业数据 |
| 众包插件加入新 Action/Scope | 可由既有授权接口扩展，无需重写 Host 基础层 |

每项保持代码 CI、真实环境发布、实际权限负向测试、页面 Human 签收与安全审计独立记账。当前本文件只是规格，未改运行时权限、未改东京/Railway、未删除数据卷，也没有启用商业计费。
