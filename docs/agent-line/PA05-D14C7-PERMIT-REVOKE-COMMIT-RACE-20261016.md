# PA05-04D14C7 — Host permit revocation vs original Object Extension commit

- **New external original source actually opened (2026-10-16):** [PostgreSQL 18 explicit blocking locks §13.4.2](https://www.postgresql.org/docs/18/applevel-consistency.html), [PostgreSQL 18 SELECT locking clauses](https://www.postgresql.org/docs/18/sql-select.html), [PostgreSQL 18 CREATE FUNCTION / SECURITY DEFINER](https://www.postgresql.org/docs/18/sql-createfunction.html). Only relevant original sections were read, not the whole manuals.
- **Source fact:** PostgreSQL explicitly states `SELECT FOR UPDATE` blocks a competing UPDATE/lock until the transaction ends; this does **not** revoke changes already committed. A `SECURITY DEFINER` entry should use a protected search path and revoke initial PUBLIC EXECUTE in the same installation transaction.
- **Our engineering deduction and test obligation:** an independent Host revocation should contend on the *same actual permit row* as the original guarded business INSERT and immutable Owner receipt. The outcome must distinguish a durable revoked-but-unused permit from an already-committed effect. A separate JS boolean cannot prove commit ordering.

## Chosen bounded implementation

- Retain original D9/D10 ticket, D14A remote ACTIVE/STOP, PA-02 Owner resource/evidence atomic transaction, D14C5 Host-only opaque 64-hex permit, D14C6 live role-drift checker and all existing physical domain triggers.
- Opt-in installation adds `revoked boolean NOT NULL DEFAULT false` to the locally protected host permit table (this table is created *only during explicit isolated installation*). A second `SECURITY DEFINER` SQL function `pa05_object_revoke_host_permit(scope, effect, exact_token)` is executable by **the same independently authenticated Host LOGIN only**, not by Business LOGIN/PUBLIC. It checks current D14C6 SQL role boundary and uses `SELECT ... FOR UPDATE` to serialize with the physical domain trigger's existing `FOR UPDATE` on that permit row.
- Host revoke returns exactly `REVOKED` for an unused permit, `COMMITTED` for a consumed permit, or `NOT_FOUND` when key and exact token do not match; repeated revoke of the same permit is idempotent `REVOKED`. The protected business trigger refuses a revoked token even with an authentic old D10 effect; the original immutable evidence INSERT may consume only an unrevoked permit. A revoked effect is **never silently reissued**, because the original one-effect durable permit row is not deleted.
- A blocked revocation does **not** cancel a running business SQL transaction. If the original Owner resource/evidence transaction commits first, revocation must return `COMMITTED` and the caller must use the original Owner verifier instead of claiming cancelled. If revocation locks and commits first, the subsequent trigger rejects a write. No unconditional blanket purge of UNKNOWN effects.

## Explicit exclusions and retained NOT_SIGNED risks

A stolen, *not-yet-revoked* permit plus compromised Business SQL credential is **not** solved by this targeted revocation feature; an attacker may race a legitimate Owner before revocation. In particular the physical trigger pins ticket and scope but **does not cryptographically bind every inserted business column and the immutable receipt payload to the exact Host-approved command**; this remains a separate payload/evidence forgery threat to test and address in the next bounded security slice. A host token must not be interpreted as production-signed command authorization. DBA/table owner can still replace triggers/functions; dual Host and Owner credential compromise, malicious Agent-input provenance, stale remote ACTIVE ticket under partition, across-instance cancellation and privileged DDL races all remain **NOT_SIGNED**. An operator must obtain genuine Owner verification, and should not assert that `COMMITTED` means the effect was rolled back.
