**Source facts:** PostgreSQL `hostssl ... scram-sha-256 clientcert=verify-ca` can require a verified client cert **in addition to** a SQL password. HBA rule order matters; the earlier matching record cannot fall through. `pg_stat_ssl` exposes server-observed TLS status and client certificate DN, issuing DN, and certificate serial, with DN truncation at 64 characters. Client cert subject DN alone does not establish a production machine identity; issuance/secret custody and certificate revocation policies are distinct controls. For a client connecting to localhost/IP, verify server SAN/IP with a trusted CA rather than disabling TLS verification.

## Bounded adopted implementation and alternatives

Only the **explicit opt-in** Object Extension installer accepts `trustedHostClientCertificate={clientDn,issuerDn,serial}`. Its existing SECURITY DEFINER SQL Host-role auditor now also demands an actual PostgreSQL server-observed client cert matching that exact approved DN/issuer/serial, on every original Host `approveCommand`, `issue`, `bindTransaction`, and `revoke`. The Business SQL LOGIN still has no access to Host SQL functions. The existing Host issuer accepts an optional CA/server-validated TLS client keypair; it does not create or manage credentials for production. D14C10 transaction PID/XID and D14C11 old-password/live-session retirement remain mandatory; no duplicate Owner/ticket/verifier or default route.

CI provisions **ephemeral, one-run certificates**, creates a real CA, server cert containing `IP:127.0.0.1`, a genuine Host client certificate and a deliberately different CA-signed client cert. Files live only in the GitHub Action temporary directories and PostgreSQL container, never in Git or log output; [setup script](../../scripts/ci/pa05-host-mtls-setup.sh) enables real worker A TLS and prepends two mutually exclusive HBA rules: `hostssl` regex for temporary Host role requiring SCRAM+CA-valid certificate, plus `hostnossl` deny rule. The original separate first-party Owner PG18 test asserts real server-observed `pg_stat_ssl`, correct Host cert authenticates and all earlier D9–D14C11 contract tests hold, stolen password **without a client certificate** cannot connect, **different trusted-CA certificate** with correct password connects but is SQL-authority rejected by exact certificate identity pin. Mandatory `PA05_ACTUAL_OBJECT_SQL_HOST_MTLS_PG`, zero skipped, exact final PR HEAD and all affected CI green.

**Rejected:** sole reliance on `application_name`, process PID, user-supplied token/GUC or SQL password as a physical certificate; `ssl` without certificate verification; `rejectUnauthorized:false`; `host` HBA fallback silently admitting the no-certificate role; wrapping these test keys into default production resources; claims that the SQL role maps to a unique hardware-backed machine or deployment workload.
