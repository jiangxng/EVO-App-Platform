## Decision

Keep the existing E01F identity + live policy boundary for the exact protected READ owner, including its action `host.plugin.lifecycle.install` or `.enable` and resource `plugin-package:evo-purchase-attention`. Before returning early on another requested package, consult the side-effect-free **actual current** AppManager `planInstall(requestedPackageId)` and the protected manifest Feature IDs. If installing or enabling a different package would include the protected package in `installPackages` or include any of its Feature IDs in `activateFeatures`, apply E01F authorization to **the protected owner**, not to the request body alias. This covers a previously uninstalled owner and a previously disabled installed owner; both are indirect mutations. No caller-supplied plan/manifest/Boolean may override the decision.

The small helper [`pa05-protected-read-lifecycle-impact.ts`](../../manager/pa05-protected-read-lifecycle-impact.ts) is loaded **only inside the existing HTTP/Action lifecycle request**, never as a startup dependency. The same `authorizePa05E01fLifecycle` is invoked from all five direct HTTP mutators and the plugin-store Action envelope. Other packages not causing a new protected dependency installation/activation continue existing behavior; other plugin Owner grants are out of scope. No new default installs, additional Action Router, worker federation or production material WRITE.

**Rejected**: matching just the posted package ID, duplicating the installer dependency resolver, authorizing via `trustApproved:true`, granting indirect activation from a permission for the requesting package instead of the protected resource, broad rewrite of all package auth during this PA05 slice, or adding startup imports of business modules.
