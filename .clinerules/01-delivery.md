# EVO 项目工作规则

目标：完成现有闭环、及时保存成果、减少重复开发。

## 开始任务
- 先检查当前分支、未提交修改和最新 main。
- 阅读项目现有开发交付规范及本任务的交接入口。
- 查清已有实现、调用者和测试，再决定是否新增功能。
- 不把历史计划当作当前完成状态；以代码、提交和验证结果为准。
- 遵循 02-project-understanding.md 的整体理解与读取要求。
- 开始前报告本任务的重要必读资料是否完整读取；
  有缺失时说明具体范围和影响。
- 项目既有权威规范为统一依据，不在本规则中重复维护其内容。

## 分析与决策
- 区分已验证事实、推断和待确认问题。
- 先说明具体问题、影响范围、最小修改及完成条件。
- 涉及接口或插件边界时，检查消费者、兼容性和迁移成本。
- 优先复用已验证能力，不重复实现，不无故增加抽象层。
- 确定性功能由代码执行；LLM 用于理解、建议和受控调用。
- 给出简短决策依据，不需要输出冗长推演。

## 执行
- 一个有界任务使用一个分支和一个 PR，连续推进。
- 已获授权且范围清楚的操作持续完成，不反复询问是否继续。
- 尊重其他窗口的文件与任务所有权，不覆盖未提交修改。
- 不扩大任务范围，不顺手启动新的治理专项。
- 遇到失败先检查证据，不重复执行相同失败操作。


## 固定验收进度表与收尾汇报（必须执行）
- 用户所称的“倒计时”，**默认指固定验收项状态跟踪表**（里程碑验收状态表、Acceptance Status Tracker），不是“3→2→1→0”或“剩余 N/M 关”的数字倒数。即使按批次实施，也以真实验收项为汇报主体。
- 对需要多步执行、跨 PR/仓库、外部验证或不能当次收尾的任务，先确定专项范围、可证实的完成条件及固定验收项；首次汇报给出该专项的完整状态表。后续每次关键进展沿用同一组验收项更新，未变动的项目也保留，便于发现偏移。
- **标准展示格式必须至少三列：验收项目｜当前状态｜下一步**。表题为“<专项名> 固定进度表（当前专项）”，最后一行为“<专项名> 整体”，归纳是否已经真正收口。按真实情况标注“已验证”“代码已验证”“未完成”“待验收”“受阻”“已合并”“已部署”等；不把测试通过、代码合并、环境部署或 Human 验收混为一谈。
- 每个验收项“下一步”写**剩余具体动作或“无需进一步操作”**；遇到阻塞写清门禁、责任归属及恢复入口。进展只能根据实际代码、CI、PR、环境与人工验收证据更新，不能为了让表格好看把“部分完成”标成已完成。
- 可在表格下补充“尚有 X 项待完成/待验收”，但**不得用数字进度条、阶段比例或 4/4 倒计时替代状态表**。不得把无限延期或新增研究伪装为进度。
- 发现必要新增验收项，应说明新增证据、变更原因和对原范围的影响；未经用户确认，不扩展专项到其他窗口任务。最后按原表逐项确认，达到完成条件后停止追加优化。
- 因权限、工具、外部系统、部署授权或其他窗口冲突暂时无法推进时，标记“受阻/待外部条件”，保留已有证据、PR/分支/提交与接续路径；不得直接宣称全部关闭。
- 多窗口先核对最新 main、开放 PR 和文档/代码 owner；不得为了表格同步编辑其他窗口的独立状态表。涉及 Agent/插件的页面改动，须保留原动作契约并做代表性回归，不得把未跑过的真实 Agent 任务宣称 PASS。
- 开发规则和专项交接文档采用**同一种表格**例行更新，单纯文字总结不代替表格。

**标准示例（内容按实际专项替换，不得复制示例状态冒充结果）：**

| 验收项目 | 当前状态 | 下一步 |
|---|---|---|
| 核心功能 | ✅ 已验证 | 最终汇总 |
| 关联工作流兼容 | ✅ 代码已验证 | 真实环境验收 |
| 实际部署 | ⏳ 待授权 | 经授权后部署 |
| 人工业务验收 | ⏳ 待验收 | 按原始数据走完整流程 |
| 专项整体 | 进行中 | 完成剩余验收后收口 |

## 验证与保存
- 按影响范围选择必要测试，避免反复全量测试。
- 修复应有与实际风险对应的验证，不能只检查代码长相。
- 达到完成条件后停止追加优化，提交并更新任务进度。
- 获得合并授权且检查通过后合入 main。
- 仅清理本任务已合并分支；不能删除则记录准确分支和提交。

## 交接
- 沿用项目现有文档体系。
- 保存完成项、未完成项、验证结果、分支、提交和下一步。
- 明确区分本地完成、已提交、已合并与已部署。
- 最终用中文简洁说明成果，不用大量技术细节淹没结论。
