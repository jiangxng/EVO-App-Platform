# 项目整体理解与资料读取规则

## 1. 先理解整体，再开展专项

首次参与项目、没有可靠交接或整体架构发生变化时：
- 先查明产品目标、模块职责、相关仓库、公共契约、
  数据归属、权限边界和开发交付规则。
- 结合代表性代码调用链验证理解，不能仅复述 README。
- 沿用现有项目文档体系保存理解结果，不另建平行知识体系。
- 区分已实现、已决定待实现、历史方案和待验证判断。

已经完成并留存的研究应复用。
后续仅核对相关变更，不在每个任务中重新研究整个项目。

## 2. 明确资料读取范围

以下与当前任务有关的文档必须完整读取：
- 适用的项目规则和开发规范；
- 本专项当前交接入口；
- 直接约束本次修改的架构决策或协议；
- 本次任务的验收与完成条件。

完整读取指读取正文从头到尾。
只读取目录、摘要、开头片段或搜索命中，不算完整读取。

其他资料可以按章节查阅，
但不得将局部阅读描述为已完整理解该文档。

## 3. 长文档与截断处理

- 先确认文档长度和章节结构。
- 文档较长时分段读取，覆盖全部必读正文。
- 工具返回截断、输出上限或省略提示时，
  必须继续读取缺失部分。
- head、前若干行、搜索摘要只能用于定位，不能替代必读。
- 文件过大或无法访问时，明确说明未读范围及影响，
  不得自行补造结论。

## 4. 保留简短阅读记录

在任务进度或交接文档中记录重要资料：
- 文件路径；
- 核对的提交或版本；
- 完整读取 / 局部读取 / 未读取；
- 局部读取的章节范围；
- 对本任务的关键约束。

只记录影响决策的重要资料，不为每个源文件建立流水账。
文档改变后，核对变更部分及其关联章节。

## 5. 专项开发前检查

动手前明确：
- 本任务归属哪个模块和专项；
- 已有实现及可复用能力在哪里；
- 是否涉及公共契约、数据归属、权限或插件生命周期；
- 是否与其他窗口工作重叠；
- 最小修改范围、必要验证和完成条件。

不确定的重要边界先核实。
不得因为实现方便而绕过平台已有机制。

## 6. 证据与诚实报告

- “已阅读”必须有实际读取依据。
- “已实现”必须有代码依据。
- “已验证”必须有实际执行结果。
- “已合并”和“已部署”必须分别确认。
- 不得把计划、推测或局部测试当作整体完成。
